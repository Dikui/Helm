## 0. 概述

### 0.1 为什么改

v5 把多智能体怎么协作写成了事先约定的规则：固定配齐四个管理者及其可见范围，并行节点之间不交互，退回只能在同一条流程内，编排只能从模板里选。实际协作是动态的，每遇到新情况就要补一条规则，新规则又和旧规则冲突。

v6 把规则分成两类：

| 类 | 内容 | 怎么处理 |
|---|---|---|
| **不变量** | 验收只能由你，或按你预先设定的自动条件；提交证据的不能核对证据；出测试的没读过这张卡的执行过程；测试不能被悄悄放宽；沙箱；预算；对外动作由你决定 | **runtime 强制**，任何 agent 都绕不过 |
| **协作约定** | 谁派单、谁和谁说话、按什么顺序做 | **降为打法**：项目负责人默认照做，遇到没预料到的情况可以当场调整 |

**一句话：runtime 只维护一块共享看板、提供协作原语、守住几道关口；怎么分工、怎么协作，由项目负责人和成员在运行时决定。**

### 0.2 本版不做实时 agent team

信箱**按轮投递**：消息在收件人这一轮结束、下一轮开始时送达，不在运行途中插入。原因：
- Codex 以 `codex exec` 一次性进程运行，runtime 控制不了它的循环，运行途中送达还没有可靠做法（任务 020 第②节）；
- 实时团队特有的难点（运行途中送达、沟通成本随人数上升、讨论不收敛）是根本性的；
- Helm 的主要场景是开发和交付，顺序依赖多、改同一批文件，实时团队收益有限。

数据模型按 agent team 的需要设计，以后升级只改投递时机（第 16 节）。

## 1. 概念

| 概念 | 含义 |
|---|---|
| **项目** | 长期存在的工作对象：指令、记忆、看板、工作现场、资源、预算。你定目标 |
| **看板** | 项目的依赖图，也是项目的全部状态，随工作推进增长 |
| **卡片** | 一份需要你单独确认规格、单独验收的交付：需求、边界、测试、交付物、依赖。可以类比为：规格是"定理陈述"，执行是"证明"，测试和独立验证是 Lean |
| **步骤** | 卡片内部由 runtime 执行并记录的一个动作（命令、单次模型调用、代理调用、人工关卡）。只是"怎么做"，不需要你单独验收 |
| **runtime** | Helm 的后台程序，**不是代理，不做判断**：保存全部状态、守住不变量、执行步骤、投递消息、记录日志、中断恢复 |
| **代理** | 代理库里的配置：人设、模型、工具 |
| **成员** | 代理在某张卡上的一次上岗。**一张卡一个成员会话**，卡片结束会话也结束 |
| **席位** | 每张卡有三个席位：**执行**（负责这张卡的成员）、**出题**（起草测试）、**验证**（判卷）。出题和验证由 runtime 拉起，每次都是新会话 |
| **项目负责人** | 每个项目一个，你和团队之间唯一的对话入口；开卡、指派、协调（3.1） |
| **答疑负责人** | 你每次"问一下"开一个，只读（3.1） |
| **打法** | 可复用的协作方式：常用的卡片组合、预设指派规则、卡内 workflow 模板。是建议，不是约定（第 9 节） |
| **标签** | "卡 X 的执行过程"。只用来判断谁不能担任出题、验证席位（第 7 节） |
| **轮** | 成员会话运行一次（一次 `codex exec` 或续接），中间可以包含一整份 workflow |

**判断放在哪一层**：需要你单独确认或验收的，开卡片（或子卡）；不需要的，作为卡内步骤。

v6 没有"流程"这一层：设计、开发、维护、调研都只是卡片上的分组标签（2.5）。

## 2. 看板与卡片

### 2.1 卡片的内容

- **规格**：需求、边界（🔒 强制 / 建议）、测试（确定性 / 证据型 / 对抗型 / 判断型，全部公开）、交付物、资料来源、上限。含义同 v5 1.4。
- **依赖**：依赖哪些卡片。
- **分组标签**：例如"设计""开发""缺陷"，可以有多个。
- **父卡**：子卡指向父卡。
- **文件声明**：执行会改哪些文件或目录（产品开发项目必填，4.6）。
- **两种版本**：**规格版本**，批准后的规格每改一次 +1；**产出版本**，每验收一次 +1。界面上分别标为"规格 v2""产出 v3"。
- **运行时数据**：负责人、尝试记录、步骤结果、证据、验收报告、交接记录、相关消息、异常记录。

### 2.2 状态

```
草稿 → 待批准 → 待依赖 → 补全 → 待指派 → 执行中 ⇄ 等待 workflow
                   │                       │
                   └→ 待处理               ├→ 等待确认 → 执行中
                                           ↓
                                         待验证 → 验证中 → 待验收 → 已验收 → 已合并 / 已发布

验证中 → 执行中（验证没通过）；待验收 → 执行中（你打回）
任何未结束状态 ⇄ 已暂停（恢复后回到暂停前的状态）
任何未结束状态 → 已取消
已验收 / 已合并 → 重开 → 待指派；改动了规格的 → 待批准
```

| 状态 | 含义 |
|---|---|
| 待批准 | 规格等批准；出题席位在这一步起草测试（5.2） |
| 待依赖 | 等上游。上游"已验收"（产品开发项目为"已合并"）才算满足，不看执行者自报 |
| 补全 | 上游都满足后，项目负责人按上游的实际产出补全规格。没变化直接进入待指派；有变化回到待批准，涉及测试的重新拉起出题席位 |
| 待指派 | 等项目负责人或打法的预设规则指派成员（3.2） |
| 等待 workflow | 成员提交了卡内计划，runtime 正在执行；发给该成员的消息排队，不唤醒它 |
| 等待确认 | "会被执行的文件"被改动，等你确认（8.6） |
| 待处理 | 有上游被取消，由项目负责人决定改依赖还是取消本卡 |
| 已暂停 | 你暂停了这张卡、它的成员或整个项目；无进展判定也会暂停（第 10 节） |
| 已取消 | 由你，或按自主度由项目负责人取消 |
| 重开 | 退回（4.1）或上游有新版本（2.4）时，已验收的卡重新执行，验收后产出版本 +1 |

- **上游已变**不是状态，是挂在卡片上的标记（2.4）。
- 成员和管理者只能**申请**状态转换，由 runtime 检查规则后执行。
- 依赖的卡片不存在、自环、成环，在批准前就拒绝。

### 2.3 开卡与批准

开卡分**提议**和**生效**两步：谁都可以提议，生效要过"规格批准"关口。

| 谁提议 | 什么时候 |
|---|---|
| 你 | 随时：在项目对话里说，或在看板上直接新建 |
| 项目负责人 | 主要开卡人：访谈后把需求拆成一组卡；处理新需求；分流发现；开审查卡、测试卡、整理教训卡 |
| 负责卡片的成员 | 把自己的卡拆成子卡；发现超出范围的问题时提交发现，生成草稿卡 |
| 答疑负责人、runtime | 不开卡 |

| 卡片类型 | 默认谁批 | 能否交给项目负责人 |
|---|---|---|
| 新目标、新范围 | 你 | **不能** |
| 父卡范围内拆出的子卡 | 你 | 能 |
| 发现生成的卡 | 你 | 能 |
| 审查卡、测试卡 | 你 | 能 |

批准前 runtime 机械检查：
1. **子卡继承父卡的 🔒 边界**：原样复制，子卡不能删改。子卡的测试不和父卡比较：父卡要等全部子卡验收后才能申请验收，那时仍要通过父卡自己的测试。
2. **测试由出题席位起草**（5.2），补齐前只能是草稿。
3. **数量上限**：每个成员同时挂着的草稿卡、看板总卡数有上限，超出时由项目负责人合并或丢弃；你建的卡不会被丢弃。

**退回**不开新卡：重开上游的卡，可以退回到任意上游（规则同 v5 1.10）。

### 2.4 依赖与版本

- 已验收的卡片就是一份可被引用的产出。重开并再次验收后产出版本 +1；旧版本保留、不可修改，可以对比差异。
- **下游不固定依赖某个版本，始终在最新的已验收产出上做**（编码项目即最新基线），不分项目类型。
- 上游出了新版本时，runtime 只给**用过旧版本的下游**打上"上游已变"标记：
  - 还没开工的下游：不受影响，直接用新版本；
  - 正在执行的下游：下一轮的上下文包里收到差异，在新版本上继续做；
  - 已验收的下游：项目负责人分析差异，给出"不受影响"或"重开"（列出受影响的卡），按自主度批准。
- 对外发布（发版本、给客户）始终由你决定。

### 2.5 分组与视图

- **分组标签**：设计、开发、维护、调研都只是标签，一张卡可以有多个。
- **视图**：看板可以按分组、依赖链、负责人、状态筛选和排布（13.3）。
- **常驻分组**：会持续进卡的分组，例如"缺陷"。新事项进来时，项目负责人（或按打法自动）展开成一条短链：诊断 → 修复 → 回归测试。
- 没有依赖的单张卡，就是 v5 的"单节点流程"。

## 3. 人员

### 3.1 管理者

| | 项目负责人 | 答疑负责人 |
|---|---|---|
| 数量与会话 | 每个项目 1 个；长期会话，过长时写交接记录后换新会话 | 你每提一个问题开一个新会话 |
| 和你的交互 | **你和团队之间唯一的对话入口**：访谈、开卡、优先级、项目指令；成员的提问由它答复或转给你 | "问一下"；起草的建议动作只交给你 |
| 职责 | 访谈（Gungnir grilling，同 v5 1.14），包括验收标准的问题；开卡、拆卡、补全规格；指派成员；排优先级、分配配额和预算；分流发现；处理退回和上游新版本；安排解决合并冲突；提炼项目记忆；汇总进度和花费 | 查清并解释异常和进度；起草建议动作（同 v5 1.13） |
| 能看到 | 全部，按需查询，默认不推送执行细节 | 全部，只读 |
| 不能做 | 验收；判断结果合不合格；替你批准不可交出的决策 | 修改任何东西 |

- **项目负责人何时被唤醒**（不在线等待）：你发消息；卡片进入待批准、补全、已验收、被退回、达到上限，或进入待指派而没有命中预设规则；成员提交发现、提问或申请加人；发给它的消息；预算到达阈值；无进展暂停。
- 项目负责人与成员、成员与成员意见不一致时交给你裁决，不互相裁决。

### 3.2 成员与指派

**谁拉起什么：**

| 谁 | 拉起什么 |
|---|---|
| 项目负责人 | 为一张卡从代理库挑代理、配预算，拉起成员 |
| runtime | 按打法的预设指派规则拉起成员；关口上的出题、验证席位；"问一下"的答疑会话 |
| 成员 | 不直接拉起；卡内 workflow 的步骤由 runtime 执行（4.4） |

**指派**（没有成员主动认领）：
1. 卡片进入"待指派"后，runtime 先查打法里的**预设指派规则**，例如"缺陷分组的卡交给代理 Y"。命中且在配额内，直接拉起成员会话。
2. 没命中或超出配额时，唤醒项目负责人，由它挑代理并指派。
3. 指派在 runtime 事务里完成，一张卡同时只有一个负责人。
4. 成员可以交还卡片，写明原因和交接记录；卡片回到"待指派"，下一个成员是新会话，从交接记录开始。

- 同时活跃的成员数默认上限 3–5，超出时卡片在"待指派"排队。
- 成员需要帮手：向项目负责人申请加人，或把一部分工作拆成子卡。
- 会话同 v5 1.17：同一个代理配置可以同时在几张卡上，**每个会话有自己的上下文包、权限配置、信箱和已读标签**，都由 runtime 生成并记录。

### 3.3 谁和谁交流

- **你只和项目负责人、答疑负责人交互。**
- 成员有问题发给项目负责人；它答不了的转给你，标明"来自卡 X 的成员"。
- 成员之间、成员与项目负责人之间通过信箱交流（第 6 节）。
- 成员的消息始终标明"来自某个 agent"，不能被当作你的指令或批准。

## 4. 卡片内部

### 4.1 一张卡从指派到验收

1. **指派**：runtime 开成员会话，发上下文包，这是第 1 轮。
2. **成员判断怎么做**（4.2）。
3. **需要 workflow 时**：成员写出计划，调用"提交计划"接口，结束这一轮，卡片进入"等待 workflow"。成员不在自己的会话里执行 workflow：步骤 agent 要由 runtime 拉起并分配权限。
4. **runtime 校验计划并逐步执行**：运行命令、发起单次模型调用、启动步骤 agent；结果和检查点存在 runtime 里。
5. **唤醒成员**：计划跑完、某一步异常或到达决策点时，runtime 唤醒成员，只给结构化结果和摘要，不给步骤的完整对话。
6. **成员决定下一步**：完成 → 提交证据、申请验证；没完成 → 修改计划进入下一轮；有需要单独验收的部分 → 拆子卡；超出范围的问题 → 提交发现；问题出在上游 → 申请退回。
7. **关口**：独立验证 → 你验收 → 合并（第 5 节）。验证没通过时，没通过的项放进下一轮的上下文包，再次唤醒成员。

### 4.2 卡片还是步骤

| 情况 | 做法 |
|---|---|
| 小改动 | 在成员会话里直接做完，不写 workflow |
| 量大、重复（如迁移 40 个调用点） | 写 workflow，runtime 执行，只把汇总交回成员 |
| 某一部分需要单独验收 | 拆成子卡 |
| 需要互相质疑（排查疑难、方案评审） | 开几张并列的卡；或在卡内分轮对抗：各自出结论 → 下一轮互相反驳 → 汇总 |

### 4.3 步骤的四档

**能用低一档就不用高一档。**

| 档 | 步骤类型 | 启动 agent 吗 | 适合 |
|---|---|---|---|
| 命令 | 已登记的测试；顺序、并行汇合、逐项处理、分支、有上限的循环、定时器 | 否 | 跑测试、确定性检查、控制顺序与展开 |
| 单次模型调用 | 给定输入，按固定格式返回结果；没有工具 | 否，只调用一次模型 | 分类、摘要、抽取、打分、两两比较、起草一段文字 |
| 代理调用 | 代理调用、验证方法调用 | **是**，每次一个新会话 | 读文件、改代码、跑命令、边查边做 |
| 人工关卡 | 人工关卡 | 否 | 中途需要你决定 |

- **步骤 agent**：默认用成员的代理配置、模型低一档（v5 1.6）；每次都是新会话，没有成员的对话历史；做完这一步就结束，不上看板、不负责卡片、没有信箱。读权限同成员，只能写本步骤声明的范围（4.6）。
- 每个步骤有执行日志、结构化结果、四态状态、检查点，可以回到检查点重做（v5 1.8、1.12）。
- 不算步骤的：成员会话自己的工具调用（作为原始输出存入日志）；执行者内部开出的子代理（runtime 看不到，在提示中约束并另行统计，v5 第 5 节）。

### 4.4 workflow

- 计划是**受约束的数据结构**，不是任意代码；runtime 解释执行，不执行模型写的代码（v5 1.6）。
- 成员可以自由组合 4.3 的步骤类型，不限于模板；模板是打法里的参考。
- **执行前校验**：字段、引用、无环、上限、预算、不得改动测试或提高权限（v5 1.6 第 1–5 条）；每个代理调用步骤都声明了写入范围，且在卡片声明之内、不含测试文件；写入范围重叠的步骤不能并行。
- 有副作用的动作先记录后执行。
- 一轮结束后可以修改计划进入下一轮，每次修改重新校验并记录；已完成步骤的结果按检查点复用。
- workflow 内的验证都是自测，不替代关口上的独立验证。

**例子：迁移 40 个调用点。** 整张卡一份计划：

```
步骤 1  代理调用：列出全部调用点 → 输出清单（runtime 冻结清单）
步骤 2  逐项处理（runtime 按清单展开）：
          2a  代理调用：只改这一个调用点（写入范围：这一项所在的文件）
          2b  已登记的测试：跑这个调用点的测试
步骤 3  单次模型调用：把 40 条结果汇总成报告
```

- 共启动 41 个步骤 agent（1 个列清单、40 个改代码）；测试由 runtime 直接运行，汇总只调用一次模型。
- 2a 的写入范围在展开时才算出来。40 个调用点分布在 12 个文件里，就最多 12 路并行，同一文件的几项排成先后；每一路在自己的工作区副本和子槽位里改代码、跑测试（4.6）。
- 成员只看到汇总，例如"37 个通过，3 个失败"，下一轮只重做那 3 个。

### 4.5 单次模型调用

- 执行者的能力声明里有一项"能否不带工具运行"。能的，直接一问一答。
- Codex 一启动就带工具循环，本版用权限配置兜底：**读**同所在卡的执行席位；**不能写任何文件**，结果只经结构化输出返回，runtime 只收这份输出；网络同其他会话。能否彻底关闭 shell 等工具，由实现任务实测（I6）。
- 以后接入能直接调用模型 API 的执行者，再换成真正的一问一答（需要凭据管理，不在本版）。
- 结果带所在卡执行过程的标签。

### 4.6 文件声明与写入范围

- **产品开发项目必须声明**：成员开工时声明会改哪些文件或目录，runtime 据此生成写权限，声明之外的写入被系统拦截。声明只能精确到文件或目录。
- **测试文件对执行方始终只读**：规格里登记的测试文件不能写进声明，执行方和步骤 agent 都改不了；要改测试只能走变更请求，由出题席位修改。
- **构建输出**：写权限 = 声明的文件 + 运行资源模板里登记的输出目录（`node_modules/`、`dist/`、测试缓存这类，通常被 `.gitignore` 忽略）。runtime 提交时只收声明内的改动；输出目录不能包含源码或"会被执行的文件"。
- **冲突**：两张进行中的卡声明重叠时，后开工的排队，或由项目负责人调整声明。执行中要改声明外的文件，申请扩大声明：没有冲突时自动批准，有冲突交项目负责人。
- **步骤的写入范围**：每个代理调用步骤在计划里声明，必须在卡片声明之内。逐项展开的步骤写成模板（如"这一项所在的文件"），展开时按冻结的清单算出实际范围再校验，落在同一文件的几项排成先后。
- **并行步骤各用一份副本**：并行步骤在 `nodes/<卡>/steps/<步骤>/` 的工作区副本里运行，各分一个子槽位，互相看不到未完成的改动；完成后 runtime 只把该步骤写入范围内的改动合回 `nodes/<卡>/`。串行步骤直接在 `nodes/<卡>/` 运行。
- 合并时按基线检查冲突（v5 1.1 合并顺序）。

现有方案的文件租约只是提示或只拦 Git 提交（任务 020 第③节）；Helm 用沙箱管目录，是真正强制的。

## 5. 关口与验证

### 5.1 关口：唯一写死的流程

```
规格批准 → 执行 → 申请验证 → 独立验证 → 你验收 → 合并 / 发布
```

| 关口 | runtime 检查什么 | 谁通过 |
|---|---|---|
| 规格批准 | 出题席位起草了测试；2.3 的机械检查 | 你，或按自主度交给项目负责人 |
| 申请验证 | 提交了证据；没有待处理的变更请求；"会被执行的文件"已确认 | runtime |
| 独立验证 | 新会话、干净的一次性副本、已读标签检查；确定性测试在沙箱内运行 | 验证席位判卷；"无法验证"由另一个新的验证席位复核 |
| 你验收 | 验收报告完整：冻结清单的每一项都有四态结果；失败、无法验证、未处理的项单独列出；核心业务逻辑改动单列 | **你**；或按你设定的自动条件由 runtime 自动验收（11.3） |
| 合并 / 发布 | 依赖已满足；基线冲突检查；有副作用的动作先记录后执行 | runtime 执行；对外发布始终由你决定 |

验证的分层（测试 / 验证方法 / 席位）、四态结果、失败反馈、验收报告沿用 v5 1.8、1.9。**不设隐藏检查**，测试全部公开，以后有需要再加。

### 5.2 出题席位

- **何时拉起**：卡片提议提交后、规格批准前；规格修改涉及测试时再拉起一次。
- **做什么**：根据需求、边界和引用的上游产出（包括已验收的方案）起草测试，为卡片选验证方法；结果和规格一起交批准人。
- **独立性**：新会话；没读过这张卡的执行过程（第 7 节）。已验收的方案是公开输入，应当读。
- **用哪个代理**：由打法或项目负责人指定，例如 Gungnir 审查代理。
- **测试本身写错**：不走退回，由新的出题席位修改，作为变更请求处理（v5 1.10）。
- **资料**：`materials/<卡>/spec/`，由 runtime 写入，只放规格、已验收的上游产出、项目指令这类公开数据；写入前检查没有本卡执行过程的标签。保留到规格批准后，卡片取消或验收后删除。
- **不写文件**：测试和验证方法经接口提交，写入规格；测试文件由 runtime 落盘，对执行方只读。不分配槽位，不运行项目代码。
- 出题席位不判卷。

### 5.3 验证席位与专用通道

- 验证席位由 runtime 在"独立验证"关口拉起：新会话，没读过这张卡的执行过程；在 `verify/<卡>/` 的一次性副本上判卷，写入不收回、不合并。
- 验证席位没有普通信箱。执行方和验证方之间只有两条格式固定的通道：
  - **执行方 → 验证方：提交证据**。只放产物、证据、覆盖清单，不放对过程的解释。
  - **验证方 → 执行方：没通过的项**。只放检查内容、输入、预期与实际、证据，由 runtime 摘出后转交。
- 每个字段规定允许来自哪里。自由文本字段可能夹带内容，要传超出字段规定的内容时（降级），由你批准（任务 020 第⑤节）。

## 6. 信箱

### 6.1 谁有信箱

| 参与者 | 信箱 |
|---|---|
| 成员、项目负责人 | 有，按会话开设 |
| 你 | 收件箱；只收项目负责人的消息和 runtime 的升级事项 |
| 验证席位 | 只有两条专用通道（5.3） |
| 出题席位、步骤 agent、答疑负责人 | 没有 |

成员可以发给：具体成员；卡片上的位置（"卡 X 的执行方"，runtime 查出当前是谁）；一组人（某个分组、全队）；项目负责人。发给没有普通信箱的对象时，消息无法送达，发件人收到原因，消息照样记入日志。

### 6.2 投递

- 消息先持久化，状态为"待投递"；收件人这一轮结束、下一轮开始时放进续接提示，变为"已投递"；收件人确认后为"已确认"。
- 空闲的收件人由 runtime 唤醒（`codex exec resume`），消息作为下一轮输入；正在运行或"等待 workflow"的收件人，消息排队。
- 每条消息有唯一 ID，重复投递时按 ID 去重；不声称"恰好一次"。
- 消息带发件人的已读标签，收件人读到后并入自己的已读标签（第 7 节）。

### 6.3 谁能看到

| 谁 | 会被推送进上下文 | 有权查看 |
|---|---|---|
| 收件人 | 发给它的消息；所在分组的广播 | 自己收发过的消息 |
| 发件人 | — | 自己发出的消息及投递状态 |
| 项目负责人 | 发给它的、全队广播 | 全部，默认不推送 |
| 其他成员 | — | 看板和所在分组的广播 |
| 你 | 项目负责人发给你的、升级给你的 | 全部 |
| 答疑负责人 | — | 全部，只读 |

## 7. 独立性：标签

**标签只决定"谁不能担任出题、验证席位"，不是读权限。** 读权限由沙箱和 runtime 导出的目录内容决定（第 8 节）。

- **只有一类标签："卡 X 的执行过程"**。挂在过程数据上：X 的执行日志、步骤结果、尝试分支与提交说明、X 的成员和步骤 agent 发出的消息、交接记录、异常记录。
- **已批准的规格、已验收的产出不带标签**。规格只有固定字段，批准就是去掉标签的一步；所以项目负责人读过执行过程后照常起草和修改规格，不影响验证席位读规格。
- **已读标签**：runtime 为每个会话记录，只增不减；续接、上下文压缩都不清除。Codex 用 shell 读了什么 runtime 看不到，所以采用保守的会话级赋予（任务 020 第⑤节，参考 FIDES）：
  1. 开工时按可读范围预先赋予：能读哪些目录、拿到什么上下文包，就先带上其中的全部标签；
  2. 运行中按接口返回追加：经接口读到的数据、收到的消息；
  3. 不该读的目录由沙箱拦截。

**runtime 强制的规则：**

| 规则 | 怎么保证 |
|---|---|
| 读过卡 X 执行过程的会话，不能担任 X 的验证方 | 验证席位开工前检查已读标签 |
| 读过卡 X 执行过程的会话，不能为 X 出题 | 出题席位开工前检查已读标签 |
| X 的执行过程不能经消息、转述流到 X 的出题、验证席位 | 这两个席位没有普通信箱；资料目录由 runtime 写入，写入前检查标签 |
| 尝试分支和提交说明不能被出题、验证席位读到 | 只能读按会话生成的仓库视图（8.4） |

出题、验证席位每次都是新会话，这几条实际防的是"runtime 给它们准备的资料里混进了执行过程"。换角色、换名字都不能去掉标签；需要独立上下文，就开新会话。

## 8. 隔离与沙箱

沿用 v5 1.20 的目录约束沙箱。

### 8.1 三层

| 层 | 管什么 | 强度 | 依据 |
|---|---|---|---|
| ① 操作系统沙箱与执行者规则 | 每个会话能读、能写哪些目录，能否联网；禁止动作清单 | 硬：系统拦截 | 任务 019：越界写被拦（S01–S03），按路径禁读有效（S05b），断网有效（S09） |
| ② runtime 控制目录内容 | 往每个目录导出什么、仓库视图里有哪些分支、接口返回什么 | 硬：agent 只看得到 runtime 放进去的东西 | v5 1.20 |
| ③ 标签 | 谁能担任出题、验证席位 | 逻辑检查 | 第 7 节 |

标签按"能读哪些目录"赋予，所以③依赖①②。

### 8.2 目录

```
~/.helm/                       runtime 私有：数据库、执行日志、经验库、验证方法
~/HelmWork/<项目>/
  repo.git                     Git 仓库本体：只有 runtime 读写
  views/<会话>/repo.git        该会话的只读仓库视图（8.4）
  nodes/<卡>/                  执行工作区：只有项目文件，没有 .git
  nodes/<卡>/steps/<步骤>/     并行步骤的工作区副本，合回后删除（4.6）
  verify/<卡>/                 验证的一次性副本：每次按提交重新导出，结束后删除
  materials/<卡>/spec/         出题资料（5.2）
  materials/<卡>/exec/         执行资料
  materials/<卡>/verify/       验证资料（证据、覆盖清单、验证方法），只在验证期间存在
  managers/<席位>/             项目负责人、答疑的工作目录
  slots/<槽位>/exec/           执行用的运行资源（并行步骤再分子槽位）
  slots/<槽位>/verify/         验证用的运行资源，每次验证前清空
```

### 8.3 每个会话的读写

| 会话 | 能写 | 能读 | 网络 |
|---|---|---|---|
| 执行（成员） | `nodes/<卡>/` 中声明的文件与登记的输出目录，测试文件除外；`slots/<槽位>/exec/` | `nodes/<卡>/`、`materials/<卡>/exec/`、`slots/<槽位>/exec/`、自己的仓库视图 | 默认开，可按卡关 |
| 步骤 agent | 本步骤的写入范围与输出目录；并行时写在自己的副本和子槽位里 | 同执行（并行时读自己的副本） | 同执行 |
| 单次模型调用 | 不写 | 同执行 | 同执行 |
| 出题 | 不写，经接口提交 | `materials/<卡>/spec/`、自己的仓库视图 | 默认开 |
| 验证 | `verify/<卡>/`、`slots/<槽位>/verify/` | 上述两处、`materials/<卡>/verify/`、自己的仓库视图 | 默认开，可按卡关 |
| 项目负责人 | `managers/项目负责人/`；其余经接口提交 | 自己的目录；项目数据经查询接口获取 | 默认开 |
| 答疑 | `managers/答疑/<问题>/`（诊断用的一次性副本） | 同左；查询接口只读 | 默认开 |

- 所有会话都**不能读**：`~/.helm`、`repo.git` 本体、其他卡片的目录、个人文件。个人文件包括 `~/.ssh`、`~/.npmrc`、`~/.gitconfig`、云服务凭据目录等：**凭据始终不进入会话可读的范围**。
- **runtime 接口**：所有会话都通过 runtime 以 stdio 方式启动的 MCP 服务调用接口（查询、提交计划、发消息、提交测试、申请验证等），与网络开关无关。调用者身份在接口进程启动时绑定，不由调用方自报；按席位授权，并记入审计日志（v5 1.20）。

### 8.4 仓库视图

`repo.git` 里有各张卡尝试分支上的中间快照和提交说明（v5 1.12），都属于执行过程。所以代理**不直接读 `repo.git`**，runtime 在会话开始时为它生成只读视图 `views/<会话>/repo.git`，会话结束后删除：

| 会话 | 视图里有什么 |
|---|---|
| 执行（成员）及其步骤 agent | 基线与已合并的历史 + 本卡自己的尝试分支 |
| 出题、验证 | 只有基线与已合并的历史 |
| 项目负责人、答疑 | 不读文件，经查询接口；答疑诊断时由 runtime 导出一次性副本 |

- 视图必须是只含允许引用的新仓库，对象只从这些引用可达；**不能**用 alternates 或共享对象目录指向完整仓库，否则凭对象哈希仍能读到其他分支。
- 基线更新后，runtime 更新正在运行的会话的视图。
- 验证用的那次提交由 runtime 导出到 `verify/<卡>/`，视图里不需要尝试分支。

### 8.5 网络与禁止动作

- **网络默认开启**，单张卡可以关闭（例如要求验证结果可复现的卡）。
- 会对外产生影响的动作写进项目设置里的**禁止动作清单**，由执行者的命令规则拦截，执行时直接被拒并记入日志。默认清单：
  - 推送与发布：`git push`、`npm publish` / `pnpm publish` / `yarn publish`、`docker push`、`gh release`、`gh pr create`、`gh pr merge`；
  - 部署：运行资源模板里登记的部署命令（如 `vercel`、`fly deploy`、`kubectl apply`）；
  - 你追加的其他命令。
- 这些动作确实需要时，由 runtime 作为有副作用的动作先记录、经你决定后执行。
- 强度说明：清单按命令匹配，用脚本间接发起请求仍可能绕过；但凭据不可读，推送、发布这类需要身份的动作仍然做不成。本版接受这个强度。

### 8.6 其他规则

- **会被执行的文件**（`package.json` 的 scripts、CI 配置、Dockerfile、依赖声明、`.vscode/`、`.codex`、`.claude`、`.agents` 等）被改动时不拦截写入，但卡片进入"等待确认"，你确认前 runtime 不在任何地方执行它们；改动在验收报告中单独列出（v5 1.20）。
- runtime 导出、预览、复制文件时不跟随指向工作区外的符号链接；安装依赖默认加 `--ignore-scripts`。

## 9. 打法与沉淀

- **打法**是一组预设，例如"产品开发"打法：
  - 新需求先开三张卡：方案设计 → 方案对抗审查 → Spec 定稿；
  - 每个增量开：实现 → 交叉代码审查 → 端到端测试 → 人工 review；
  - 异常解决后开整理教训卡；
  - 预设指派规则（某个分组或某类卡默认交给哪个代理）；
  - 出题、验证席位默认用的代理；卡内 workflow 模板。
- **审查类的卡**（交叉代码审查、浏览器检查、端到端测试）不另设独立性检查：一张卡一个新会话，审查方本来就不带被审卡的记忆，起作用的是代理的配置和工具。打法建议审查卡的上下文包只放被审卡的产出和规格，不放执行过程。
- 打法只是建议。项目负责人偏离打法时，在决策记录里写明理由；不需要批准，你能看到和撤销。
- **沉淀路径**：行之有效的协作方式 → 保存为打法 → 高频且需要稳定的，固化为卡片模板或 workflow 模板。新打法和新版本经你审核后入库。
- 其余沉淀（验证方法、经验库、项目记忆、代理进化）沿用 v5 第 3 节、1.16、1.17、1.18。整理异常教训由"整理教训卡"承担：异常解决后由项目负责人开卡，交付物是教训草稿与验证方法更新，你审核后入库。

## 10. 预算与停止

- 预算分三层：项目、成员、卡片。卡内 workflow 的并发、调用次数、重试次数受卡片预算约束（v5 1.6 第 4 条）。
- **无进展判定**：一张卡连续 N 轮没有新的通过项，或一个成员连续 N 轮没有产出，就暂停并交给项目负责人；它也处理不了的升级给你。**N 默认 3**，可在项目设置中修改。
- 消息计入发件人预算；广播有频率上限。
- 达到上限的处理同 v5 B7。

## 11. 自主度

### 11.1 记录

- 所有决策写入决策记录：决策者（你 / 项目负责人 / runtime 自动）、"原样采纳 / 有修改 / 驳回"，并统计采纳率。
- 项目负责人偏离打法时也写一条，附理由。

### 11.2 授权

- **判断类的决定只能交给项目负责人**。成员不能接受授权，项目负责人也不能转授。
- **机械类的决定**由你预先设定条件、runtime 执行：自动验收、无冲突时扩大文件声明、标为"默认自动"的项。"无法验证"交出后由新的验证席位复核。
- **粒度**：项目级默认值，可以按分组标签覆盖。例如"缺陷"分组的子卡交给项目负责人批，"设计"分组的仍由你批。
- **授权只改变"谁批准"，不改变"检查什么"**：2.3 的机械检查、第 7 节的标签规则、第 5 节的关口检查照常执行。

### 11.3 决策点

**规格**

| 决策点 | 能否交出 | 交出后 |
|---|---|---|
| 新目标、新范围的卡 | ❌ | 始终由你批准 |
| 访谈（新目标开工前） | ❌ | 始终由项目负责人与你访谈 |
| 父卡范围内拆出的子卡 | ✅ | 项目负责人批准 |
| 发现生成的卡 | ✅ | 项目负责人分流并批准 |
| 审查卡、测试卡 | ✅ | 项目负责人批准 |
| 规格补全有变化 | ✅ | 项目负责人批准 |
| 变更请求：不放宽测试 | ✅ | 项目负责人批准 |
| 变更请求：放宽测试或边界 | ❌ | 始终由你批准 |
| 取消卡片 | ✅（新范围的卡除外） | 项目负责人取消，写明理由 |

**执行**

| 决策点 | 能否交出 | 交出后 |
|---|---|---|
| 配额内拉起成员、指派卡片 | 默认已交给项目负责人；预设指派规则由 runtime 执行 | — |
| 超出配额（成员数、并发、模型额度） | ❌ | 始终由你改 |
| 扩大文件声明：没有冲突 | 默认自动 | runtime 直接批准 |
| 扩大文件声明：有冲突 | ✅ | 项目负责人调整或排队 |
| workflow 计划执行前确认 | 默认自动 | 可改为"由我确认" |
| 上下文包确认 | 默认自动 | 可改为"派单前由我确认" |
| 退回请求 | ✅ | 项目负责人批准 |
| 上游新版本：已验收的下游"不受影响"或"重开" | ✅ | 按项目负责人的结论执行 |
| 达到上限 | ✅ | 在你设定的额度内自动追加，额度用完升级给你 |
| 无进展暂停后的处理（换人、拆卡、调整依赖） | ✅ | 项目负责人处理；取消新范围的卡仍需你 |

**验证与验收**

| 决策点 | 能否交出 | 交出后 |
|---|---|---|
| 判定"无法验证" | 由你设定 | 新的验证席位复核，不经项目负责人 |
| 验收 | 由你设定 | runtime 执行：全部测试通过且没有判断型测试时自动验收；有判断型测试的仍由你验收 |
| "会被执行的文件"被改动 | ❌ | 始终由你确认 |
| 专用通道降级 | ❌ | 始终由你批准 |
| 合并到基线 | 默认自动 | 验收后由 runtime 执行 |
| 不可逆或对外的动作 | ❌ | 始终由你决定 |
| 副作用状态不明 | ❌ | 始终由你决定 |

**记忆与沉淀**

| 决策点 | 能否交出 | 交出后 |
|---|---|---|
| 项目记忆：注意事项 | 默认自动 | 你可以查看、撤销 |
| 项目记忆：设计决策 | ❌ | 始终由你确认 |
| 新打法、经验库条目、验证方法入库 | ❌ | 始终由你审核 |
| 新建代理 | ❌ | 管理者只能提议 |
| 分歧 | ❌ | 始终由你裁决，附双方理由 |

### 11.4 统计与撤销

- 采纳率只用于提出建议（例如"过去 30 次子卡批准你都原样采纳，是否交给项目负责人"），是否切换由你决定。
- 被代做的决定可以回看和撤销。撤销按"重开"处理：受影响的下游重新验证，不受影响的保留（v5 1.10）。

## 13. 界面

### 13.1 整体布局

- **顶栏**：项目名、预算与花费、活跃成员数、收件箱计数、暂停按钮（B24）。

### 13.2 收件箱

只列需要你处理的事：
- **待回答**：访谈、项目负责人的提问（含转来的成员提问）；
- **待批准**：规格（标明新范围 / 子卡 / 发现 / 审查或测试卡 / 补全有变化）、变更请求、退回请求、通道降级；
- **待验收**；
- **需要处理**：达到上限、无进展暂停、上游新版本、合并冲突、超出配额的申请、人工关卡、副作用状态不明；
- **需要确认**："会被执行的文件"被改动、设计决策、分歧；
- **待审核**：新打法、经验库条目、验证方法、代理提议。

每一项链接到对应的卡、消息或对话。被自动处理的决定不进收件箱，在决策记录里回看和撤销。

### 13.3 看板

| 视图 | 显示什么 | 用途 |

## 15. 原型分批

### 15.1 原型 v4 能复用多少

v4（`prototype/index.html`，约 5900 行的单个文件，纯前端模拟）按"项目 → 流程 → 节点"建模：

| 部分 | v6 怎么处理 |
|---|---|
| 侧栏、收件箱外框、面包屑 | 复用，调整分组 |
| 流程图的分层布局与连线（含滚动、焦点小图） | 复用为依赖图视图 |
| 可视化编辑（拖线改依赖、新增节点、改动清单） | 复用为 B3 |
| 节点详情的标签页框架、四态结果报告、步骤图、上下文包、版本差异 | 复用，按 13.5 重新分页 |
| 产出物预览、决策记录、代理库、经验库、项目记忆 | 基本复用 |
| **数据模型**（项目 / 流程 / 节点 / leader / 三种席位） | **重写**为项目 / 看板 / 卡片 / 成员 / 消息 / 标签，几乎所有渲染函数跟着改 |
| 状态列、成员、回放视图；项目对话；消息时间线；团队页；打法库 | **新做** |

结论：界面组件约一半可以复用，但数据模型要重写，会波及几乎所有页面。所以第 1 批先换数据模型，并保证复用的页面在新模型上照常工作。

每批一个实现任务加一个浏览器检查任务（浏览器检查通过后实现任务才算完成）。任务号从 021 起。

## 16. 升级到实时 agent team

数据模型已包含 team 需要的一切：看板、指派、按会话的信箱、消息标签、专用通道。升级只改：

1. **投递时机**：从"轮与轮之间"改为"运行途中"。前提是 Codex 实测（任务 020 第⑥节 T1、T2、T3、T6、T7）证明能经 runtime 的 MCP 工具返回夹带消息，且延迟可控；
2. **轮次长短**：成员可以更长时间连续运行，靠消息当场纠偏；
3. **广播**："我改主意了"这类广播在运行途中送达，需要更严格的频率和预算控制。
