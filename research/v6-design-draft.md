## 0. 为什么改

v5 把多智能体怎么协作写成了事先约定的规则：固定配齐四个管理者及其可见范围，并行节点之间不交互，退回只能在同一条流程内，编排只能从模板里选、清单冻结。实际协作是动态的，每遇到一个新情况就要补一条规则，新规则又和旧规则冲突。

v6 把规则分成两类，分别对待：

| 类 | 是什么 | v6 怎么处理 |
|---|---|---|
| **不变量** | 保护你的规则：只有你能验收；提交证据的不能核对证据，出测试的不能做方案；测试不能被悄悄放宽；沙箱；预算；对外动作由你决定 | **runtime 强制**，任何 agent 都绕不过 |
| **协作约定** | 规定 agent 之间怎么配合：谁派单、谁和谁不能说话、按什么顺序做 | **降为默认打法**：项目负责人默认照做，遇到打法没预料到的情况可以当场调整 |

**一句话：runtime 只做三件事——维护一块共享看板、提供协作原语、守住几道硬关口；怎么分工、怎么协作，由项目负责人和成员在运行时决定。**

### 0.1 本版不做实时 agent team

动态编排不依赖成员之间的实时通信。本版的信箱**按轮投递**：消息在收件人这一轮结束、下一轮开始时送达，不在运行途中插入。原因：

- Codex 以 `codex exec` 一次性进程运行，runtime 控制不了它的循环，运行途中送达尚无可靠做法（任务 020 第②节）；
- agent team 特有的难点（运行途中送达、沟通成本随人数快速上升、讨论不收敛）是根本性的，只能缓解；
- Helm 的主要场景是开发和交付，顺序依赖多、改同一批文件，实时团队的收益有限。

**升级路径**：看板、卡片、认领、信箱、标签、关口的数据模型都按 agent team 的需要设计。以后升级为实时团队，只改消息的投递时机，其余不变（见第 12 节）。

## 1. 术语与分层

| 层 | 是什么 | 谁来定 | 你的参与 |
|---|---|---|---|
| **项目** | 长期存在的工作对象：指令、记忆、看板、工作现场、资源、预算 | 你 | 定目标 |
| **看板** | 项目的依赖图，也是项目的全部状态；随工作推进增长 | 项目负责人和成员提议，按自主度批准 | 批准卡片；随时查看 |
| **卡片**（原节点） | 一份相对独立的交付：需求、边界、测试、交付物、依赖 | 提议人起草需求和边界，另一个会话起草测试 | 确认规格；**最终验收** |
| **步骤** | 卡片内部一次由 runtime 拉起并记录的动作（代理调用或检查） | 认领卡片的成员安排 | 不参与，可以查看 |

- **判断一件事放在哪一层**：需要你单独确认或验收的是卡片；只是"怎么做"的是步骤。
- **runtime**：Helm 的后台程序，**不是代理，不做判断**。保存全部状态、守住不变量、执行步骤、投递消息、记录日志、中断恢复。
- **成员**：坐在会话里干活的 agent。代理（代理库里的配置）是"人设和技能"，成员是它在本项目的一次上岗。
- **打法**：可复用的协作方式，例如一组预设的卡片、默认拉起的角色、卡内 workflow。打法是给项目负责人的**建议**，不是必须遵守的约定。

**v5 的"流程"一层取消**：阶段标签（设计、开发、维护、调研……）变成看板上的分组与视图（见 2.6）。（D1 已定）

## 2. 看板与卡片

### 2.1 卡片

每张卡片有：
- **规格**：需求、边界（🔒 强制 / 建议）、测试（确定性 / 证据型 / 对抗型 / 判断型，可含隐藏检查）、交付物、资料来源、上限。规格的含义同 v5 1.4。
- **依赖**：依赖哪些卡片的哪个版本。
- **分组标签**：例如"设计""开发""缺陷"，可以有多个。
- **父卡**：子卡指向它的父卡。
- **文件声明**：执行会改哪些文件或目录（产品开发项目必填，见 2.5）。
- **运行时数据**：认领人、尝试记录、步骤结果、证据、验收报告、交接记录、相关消息、异常记录。

可以借用费马项目的类比：卡片规格是"定理陈述"，执行是"证明"，测试和独立验证就是 Lean。

### 2.2 卡片状态（由 runtime 管理）

```
草稿 → 待批准 → 待依赖 → 可认领 → 执行中 → 待验证 → 验证中 → 待验收 → 已验收 → 已合并 / 已发布
                                     │                      │
                                     └── 等待确认（会被执行的文件被改动，见 v5 1.20）
任何未结束状态 → 已取消（由你或按自主度由项目负责人决定）
已验收 / 已合并 → 重开（退回或产生新版本）→ 执行中
```

- 成员和管理者只能**申请**状态转换，runtime 检查规则后执行。
- **依赖解锁看验收，不看执行者自报**：上游"已验收"（产品开发项目为"已合并"）后，下游才从"待依赖"变为"可认领"。"已取消"的上游不算满足依赖，下游进入"待处理"，由项目负责人决定改依赖还是取消。
- 依赖的卡片不存在、自环、成环，在批准前就拒绝。

### 2.3 开卡：谁提议、谁批准

开卡分**提议**和**生效**两步。谁都可以提议，生效要过"规格批准"关口。

| 谁 | 什么时候提议 |
|---|---|
| 你 | 随时：在项目对话里说，或直接在看板上新建 |
| 项目负责人 | 主要开卡人：访谈后把需求拆成一组卡；处理新需求；分流发现 |
| 认领了卡的成员 | 把自己的卡**拆成子卡**；做着发现超出范围的问题时**提交发现**，生成草稿卡 |
| 默认拉起的流程负责人、质量负责人 | 在自己负责的分组里补卡、拆卡；整体审查卡、测试卡 |
| 答疑负责人 | 不开卡，只起草建议交给项目负责人 |
| runtime | 不开卡 |

| 卡片类型 | 默认谁批 | 能否交给项目负责人 |
|---|---|---|
| 新目标、新范围 | 你 | **不能** |
| 在父卡需求和边界之内拆出的子卡 | 你 | 能（D2 已定：默认由你批）|
| 发现生成的卡 | 你 | 能 |
| 审查卡、测试卡 | 你 | 能 |

runtime 在批准前机械检查：
1. **子卡不能放宽父卡**：子卡的边界和测试不能比父卡松；父卡要等全部子卡验收后才能申请验收。
2. **测试和方案出自不同会话**：测试必须由没读过该卡方案草稿的会话起草（按标签判断，见第 5 节）；补齐前只能是草稿。
3. **数量上限**：每个成员同时挂着的草稿卡、看板的总卡数有上限，超出时交给项目负责人合并或丢弃。

两种情况**不开新卡，改已有的卡**：
- **退回**：重开上游的卡（v5 1.10 的规则照旧，但**不再限于同一条流程**）；
- **上游出了新版本**：见 2.4。

### 2.4 版本：取代 v5 的"发布产出"

- 已验收的卡片就是一份可被引用的产出。卡片被**重开并再次验收**，产生新版本（v1、v2……），旧版本不可修改。
- 下游依赖的是**指定版本**。上游出了新版本后，runtime 顺着依赖边把下游标为"上游已变"，由下游的负责人分析差异，给出"直接升级"或"重做"（列出受影响的卡）的结论，按自主度由你批准。规则同 v5 1.3，只是不再需要单独的发布产出对象。
- 对外发布（发版本、给客户）仍是人工关口，始终由你决定。

### 2.5 文件声明与冲突

- 产品开发项目中，认领卡片时必须声明会改哪些文件或目录。runtime 据此生成该卡工作区的**写权限**（v5 1.20 的目录约束沙箱），声明之外的写入被系统拦截，**是强制的，不是提示**。
- 两张进行中的卡声明有重叠时，后认领的进入排队，或由项目负责人调整声明。
- 执行中发现需要改声明之外的文件：申请扩大声明，有冲突时交项目负责人处理。
- 合并时仍按基线检查冲突（v5 1.1 合并顺序照旧）。

任务 020 第③节：现有方案的文件租约都只是提示，或只拦 Git 提交；Helm 用沙箱管目录，可以做成真正强制。

### 2.6 分组与视图：取代 v5 的"流程"

- **分组标签**取代阶段标签：设计、开发、维护、调研……都只是标签，一张卡可以有多个。
- **视图**：看板可以按分组、按依赖链、按负责人、按状态筛选和排布。v5 的"流程图"就是某个分组在依赖图上的投影。
- **常驻流程**变成一类会持续进卡的分组，例如"缺陷"：新事项进来时，项目负责人（或按打法自动）展开成一条短链卡片（诊断 → 修复 → 回归测试）。
- **单节点流程**就是一张没有依赖的卡。
- **流程模板**变成打法（见第 9 节）。

## 3. 成员

### 3.1 谁拉起成员

| 谁拉起 | 拉起什么 | 理由 |
|---|---|---|
| **项目负责人** | 成员：从代理库挑一个代理，配上预算 | 组队是判断，判断归负责人 |
| **runtime** | 关口上的验证席位；你每次"问一下"时的答疑会话 | 独立性不能依赖 agent 自觉 |
| **成员自己** | 卡内的 subagent 或 workflow worker（经 runtime 拉起，记为步骤） | 只为这张卡干活，不上看板，不能认领别的卡 |

- 同时活跃的成员数受配额限制（默认 3–5），超出时排队。
- 成员需要帮手：向项目负责人申请加人，或把一部分工作拆成子卡放回看板。

### 3.2 认领与指派
- 卡片变为"可认领"后，**空闲成员可以自己认领**；项目负责人也可以**直接指派**（例如需要特定专长）。
- 认领在 runtime 事务里完成（比较版本和认领人），不会两人同时认领一张卡。
- 卡片在等、没有空闲成员时，由项目负责人决定是否再拉一个人。
- 成员可以放弃认领，写明原因和交接记录。

### 3.3 会话
- 同 v5 1.17：代理配置与会话分开；同一个代理配置可以同时坐几个位置，**每个会话单独的上下文包、权限配置、信箱和标签记录**。
- 隔离靠会话 ID、上下文包、权限配置三者不同，都由 runtime 生成并记录。

## 4. 卡片内部怎么做

由认领的成员决定：

| 情况 | 做法 |
|---|---|
| 小改动 | 一个会话直接做完，整张卡只有一个步骤 |
| 量大、重复（迁移 120 个调用点） | **workflow**：成员写出计划，runtime 校验后执行，中间结果存在 runtime 里，只把汇总交回成员 |
| 某一部分需要单独验收 | 拆成子卡放回看板 |
| 需要互相质疑（排查疑难、方案评审） | 开几张并列的卡，或在卡内用对抗验证模式**分轮**进行：各自出结论 → 下一轮互相反驳 → 汇总 |

规则只有一条：**需要单独验收的，开子卡；不需要的，作为卡内步骤。**

### 4.1 步骤
- 定义：**runtime 拉起并记录的每个动作**，包括 workflow 中的每次代理调用、成员申请拉起的 subagent、每次运行测试。
- 不算步骤：成员会话内部自己的工具调用和思考（作为原始输出存入日志）；执行者内部自行开出的子代理（runtime 看不到，在提示中约束并另行统计，见 v5 第 5 节）。
- 每个步骤有执行日志、结构化结果、四态状态、检查点，可以回到检查点重做（同 v5 1.8、1.12）。

### 4.2 workflow（取代 v5 的"只能从模板选"）
- 成员写出计划，形式仍是**受约束的数据结构**，不是任意代码；runtime 解释执行，不执行模型写的代码（v5 1.6）。
- **放开**：不再限定只能从模板选，成员可以自由组合允许的步骤类型（v5 1.6 的十种）。模板变成打法里的参考。
- **保留**：执行前校验（字段、引用、无环、上限、预算、不得放宽测试或提高权限，v5 1.6 第 1–5 条）；有副作用的动作先记录后执行。
- **新增**：一轮结束后可以修改计划进入下一轮，每次修改重新校验并记录；已完成步骤的结果按检查点复用。
- workflow 内的验证都是自测，不替代关口上的独立验证。

## 5. 标签与独立性（取代固定角色的可见范围表）

v5 用"四个管理者各能看到什么"的固定表格保证独立性。v6 改为**按会话读过什么来机械判断**。

### 5.1 标签
- 每条数据带标签，例如"卡 X 的执行过程""卡 X 的隐藏检查""卡 X 的方案草稿"。
- runtime 为每个会话记录**已读标签**，只增不减；续接、上下文压缩都不清除。

### 5.2 标签怎么赋给会话
Codex 用 shell 读了什么文件，runtime 看不到。所以采用**保守的会话级标签**（任务 020 第⑤节，参考 FIDES）：
1. **开工时按可读范围预先赋予**：会话能读哪些目录、拿到什么上下文包，就先带上这些内容的全部标签；
2. **运行中按接口返回追加**：经 runtime 接口读到的数据、收到的消息，把其标签并入；
3. **沙箱禁读兜底**：不该读的目录由 v5 1.20 的读规则系统级拦截。

### 5.3 不变量（runtime 强制）
| 规则 | 判断方式 |
|---|---|
| 读过卡 X 执行过程的会话，不能担任 X 的验证方 | 验证席位开工前检查已读标签 |
| 起草过 X 方案的会话，不能为 X 起草测试 | 测试提交时检查已读标签 |
| X 的隐藏检查，只有 X 的验证方和你能读 | 隐藏检查只在验证期间写入验证席位的资料目录（v5 1.20） |
| 带标签的内容不能借消息、摘要、转发间接流到不该读的人那里 | 消息继承发件人的已读标签，投递前检查（见 6.3） |

换角色、换名字都不能"降级"标签；需要独立上下文，就开新会话。

## 6. 信箱（按轮投递）

### 6.1 收件人
"收件人"指这条消息发给了谁，不是一个职位。

| 参与者 | 信箱 |
|---|---|
| 成员、项目负责人、默认拉起的流程负责人和质量负责人 | 有，按会话开设 |
| 你 | 有，就是界面上的收件箱 |
| 验证席位 | 只有专用通道，不收普通消息 |
| 答疑负责人 | 没有，只读不参与协作 |

收件人可以写：具体成员；卡片上的位置（"卡 X 的执行方"，runtime 查出当前是谁）；一组人（某个分组、全队）；你。

### 6.2 投递时机
- **按轮投递**：消息先持久化，状态为"待投递"。收件人这一轮结束、下一轮开始时，runtime 把待收消息放进续接提示，状态变为"已投递"。收件人确认后为"已确认"。三种状态分开记录。
- **空闲的收件人**：收到消息时由 runtime 唤醒（`codex exec resume`），这条消息作为下一轮输入。
- **正在运行的收件人**：消息排队，等这一轮结束。
- 同一条消息有唯一 ID，重复投递时接收方按 ID 去重；不声称"恰好一次"。

### 6.3 谁能看到
区分**有权查看**和**会被推送进上下文**：

| 谁 | 会被推送 | 有权查看 |
|---|---|---|
| 收件人 | 发给它的消息；它所在分组的广播 | 自己收发过的消息 |
| 发件人 | — | 自己发出的消息及投递状态 |
| 你 | 发给你的、升级给你的（进收件箱） | **全部** |
| 答疑负责人 | — | **全部，只读** |
| 项目负责人 | 发给它的、全队广播 | 全部，默认不推送 |
| 其他成员 | — | 只看得到看板和所在分组的广播 |

**消息也是数据**：消息继承发件人的全部已读标签，投递前检查收件人能否读取。不能读的不投递，发件人收到"无法送达"和原因，消息照样记入日志。转述也绕不过：转述人读过原消息，就带上同样的标签。

成员的消息始终标明"来自某个 agent"，不能被当作你的指令或你的批准。

### 6.4 两条专用通道
被标签挡住的人之间，只能经过格式固定的通道传递必要信息：
- **执行方 → 验证方：提交证据**。只放产物、证据、覆盖清单。
- **验证方 → 执行方：没通过的项**。只放检查内容、输入、预期与实际、证据，由 runtime 摘出后转交；这一项隐藏检查从此公开，通过的继续保密（同 v5 1.9）。

每个字段规定**允许来自哪里**；自由文本字段同样可能夹带内容，所以格式固定不等于自动安全，必要时由你批准（任务 020 第⑤节）。

## 7. 关口（唯一写死的流程）

每张卡都必须走：

```
规格批准 → 执行 → 独立验证 → 你验收 → 合并 / 发布
```

| 关口 | runtime 检查什么 | 谁通过 |
|---|---|---|
| 规格批准 | 2.3 的三条机械检查；测试与方案出自不同会话 | 你，或按自主度交给项目负责人 |
| 申请验证 | 执行方提交了证据；没有待处理的变更请求；"会被执行的文件"已确认 | runtime |
| 独立验证 | 验证席位由 runtime 拉起：新会话、干净的一次性副本、已读标签检查；确定性测试在沙箱内运行 | 验证席位判卷 |
| 你验收 | 验收报告完整（失败、无法验证、未处理的项单独列出；核心业务逻辑改动单列） | **你**；或按自主度"全部测试通过即自动验收" |
| 合并 / 发布 | 依赖已满足；基线冲突检查；有副作用的动作先记录后执行 | runtime 执行；对外发布始终由你决定 |

验证的分层（测试 / 验证方法 / 席位）、四态结果、隐藏检查、失败反馈、验收报告，全部沿用 v5 1.8、1.9。

## 8. 管理者

| | 项目负责人 | 答疑负责人 |
|---|---|---|
| 数量与会话 | 每个项目 1 个；长期会话，过长时写交接记录后换新会话 | 你每提一个问题开一个新会话 |
| 和你的交互 | **你唯一的对话入口**：访谈、开卡、优先级、项目指令 | "问一下" |
| 职责 | 访谈（Gungnir grilling，同 v5 1.14）；开卡、拆卡；拉起成员、指派；排优先级、分配配额和预算；分流发现；处理退回和上游新版本；安排解决合并冲突；提炼项目记忆；汇总进度和花费 | 查清并解释异常、进度；起草建议动作（同 v5 1.13） |
| 能看到 | 全部，按需查询，默认不推送执行细节；**隐藏检查除外** | 全部，只读，含隐藏检查 |
| 不能做 | 验收；判断结果合不合格；替你批准不可交出的决策 | 修改任何东西 |

- **流程负责人、质量负责人不再强制配置**，变成打法里**默认拉起的角色**：
  - 流程负责人：管一组卡片的规格起草、补全、本组的提问和退回；
  - 质量负责人：起草测试（含隐藏检查）、选验证方法、组织方案对抗审查、检查验收报告完整性、整理异常教训。
  - 它们是成员，遵守同样的标签规则；"出测试的不能是做方案的"由标签保证，不再靠岗位。
- **项目负责人何时被唤醒**（不在线等待）：你发消息；卡片状态变化（待批准、已验收、被退回、达到上限）；成员提交发现或申请加人；发给它的消息；预算到达阈值；"连续 N 轮没有进展"。
- 管理者之间意见不一致时交给你，不互相裁决（同 v5）。

## 9. 打法与沉淀

- **打法**：一组预设，例如"产品开发"打法：开工时拉起流程负责人和质量负责人；新需求先开方案设计 → 方案对抗审查 → Spec 定稿三张卡；每个增量开实现 → 交叉代码审查 → 端到端测试 → 人工 review。v5 的流程模板、节点模板都变成打法。
- 打法只是给项目负责人的建议。项目负责人偏离打法时，在决策记录里写明理由。
- **沉淀路径**：项目中行之有效的协作方式 → 保存为打法 → 高频且需要稳定的 → 固化为卡片模板或卡内 workflow 模板。新打法和新版本经你审核后入库。
- 其余沉淀（验证方法、经验库、项目记忆、代理会进化）沿用 v5 第 3 节、1.16、1.17、1.18。

---

## 10. 预算与停止

- 预算分三层：项目、成员、卡片；卡内 workflow 的并发、调用次数、重试次数受卡片预算约束（v5 1.6 第 4 条）。
- **无进展判定**：卡片连续 N 轮没有新的通过项，或成员连续 N 轮没有产出，暂停并交给项目负责人；项目负责人也处理不了的升级给你。
- 消息计入发件人预算；广播有频率上限。
- 达到上限的处理同 v5 B7。

## 13. 升级到实时 agent team 的路径

本版的数据模型已经包含 team 需要的一切：看板、认领、按会话的信箱、消息标签、专用通道。升级只改：

1. **投递时机**：从"轮与轮之间"改为"运行途中"。前提是 Codex 实测（任务 020 第⑥节 T1、T2、T3、T6、T7）证明可以经 runtime 的 MCP 工具返回夹带消息，并且延迟可控；
2. **轮次的长短**：成员可以更长时间连续运行，靠消息当场纠偏；
3. **广播的语义**："我改主意了"这类广播在运行途中送达，需要更严格的频率和预算控制。

## 16. 自主度（取代 v5 第 4 节）

### 16.1 记录
- 所有决策都写入决策记录，标注决策者（你 / 项目负责人 / runtime 自动）以及"原样采纳 / 有修改 / 驳回"，并统计采纳率（同 v5）。
- 项目负责人**偏离打法**时，也写一条决策记录并附理由；不需要批准，但你能看到和撤销。

### 16.2 授权的对象和粒度
- **只能交给项目负责人**。默认拉起的流程负责人、质量负责人是成员，不能直接接受授权；项目负责人也不能把授权再转交给别人。这样每个被代做的决定，都能追到同一个对你负责的人。
- **粒度**：项目级默认值，可以按**分组标签**覆盖。例如"缺陷"分组的子卡交给项目负责人批，"设计"分组的仍由你批。（v5 是按流程模板设置，流程取消后改为按分组。）
- **授权只改变"谁批准"，不改变"检查什么"**：第 2.3 节的三条机械检查、第 5 节的标签规则、第 7 节的关口检查，无论谁批准都由 runtime 照常执行。

### 16.3 决策点

**规格**

| 决策点 | 能否交给项目负责人 | 交出后的行为 |
|---|---|---|
| 新目标、新范围的卡 | ❌ | 始终由你批准 |
| 访谈（新目标开工前） | ❌ | 始终由项目负责人与你访谈 |
| 父卡范围内拆出的子卡 | ✅ | 项目负责人批准后生效 |
| 发现生成的卡 | ✅ | 项目负责人分流并批准 |
| 审查卡、测试卡 | ✅ | 项目负责人批准后生效 |
| 依赖解锁前的规格补全 | ✅ | 没有变化直接开工；有变化由项目负责人批准 |
| 变更请求：不放宽测试 | ✅ | 项目负责人批准 |
| 变更请求：放宽测试或边界 | ❌ | 始终由你批准 |
| 取消卡片 | ✅（新范围的卡除外） | 项目负责人取消，写明理由 |

**执行**

| 决策点 | 能否交给项目负责人 | 交出后的行为 |
|---|---|---|
| 在配额内拉起成员、指派卡片 | 默认已交给项目负责人 | — |
| 超出配额（成员数、并发、模型额度） | ❌ | 配额是项目设置，始终由你改 |
| 扩大文件声明：没有冲突 | 默认自动 | runtime 直接批准 |
| 扩大文件声明：有冲突 | ✅ | 项目负责人调整或排队 |
| 卡内 workflow 计划执行前确认 | 默认自动 | 可改为"由我确认" |
| 上下文包确认 | 默认自动 | 可改为"派单前由我确认" |
| 退回请求 | ✅ | 项目负责人批准 |
| 上游新版本：直接升级或重做 | ✅ | 按负责人的结论执行 |
| 达到上限 | ✅ | 在你设定的额度内自动追加；额度用完升级给你 |
| 无进展暂停后的处理（换人、拆卡、调整依赖） | ✅ | 项目负责人处理；要取消新范围的卡仍需你 |

**验证与验收**

| 决策点 | 能否交给项目负责人 | 交出后的行为 |
|---|---|---|
| 判定"无法验证" | ✅ | 交给另一个新上下文的验证席位判定，不由项目负责人自己判 |
| 验收 | ✅ | 全部测试通过、且没有判断型测试时，自动验收；有判断型测试的仍由你验收 |
| "会被执行的文件"被改动 | ❌ | 始终由你确认 |
| 专用通道中超出字段规定的内容（降级） | ❌ | 始终由你批准 |
| 合并到基线 | 默认自动 | 验收后由 runtime 执行 |
| 不可逆或对外的动作（发布、发给客户） | ❌ | 始终由你决定 |
| 副作用状态不明的处理 | ❌ | 始终由你决定 |

**记忆与沉淀**

| 决策点 | 能否交给项目负责人 | 交出后的行为 |
|---|---|---|
| 项目记忆：注意事项 | 默认自动 | 你可以查看、撤销 |
| 项目记忆：设计决策 | ❌ | 始终由你确认 |
| 新打法、经验库条目、验证方法入库 | ❌ | 始终由你审核 |
| 新建代理 | ❌ | 管理者只能提议，你批准或直接创建 |
| 管理者或成员之间的分歧 | ❌ | 始终由你裁决，附双方理由 |

### 16.4 与 v5 相比的变化

| 变化 | 原因 |
|---|---|
| 授权对象从"四个管理者分别授权"改为只有项目负责人 | 流程负责人、质量负责人降为成员 |
| 授权粒度从"按流程模板"改为"按项目默认 + 分组覆盖" | 流程层取消 |
| 新增：取消卡片、扩大文件声明、超出配额、无进展处理、专用通道降级、偏离打法记录 | 新设计的新决策点 |
| 拆开"变更请求"：不放宽测试可以交出，放宽测试始终由你 | v5 只写了"不放宽测试时自动批准"，放宽的情况没写明 |
| 自动验收加了前提：没有判断型测试 | v5 写的是"所有测试通过即自动验收"，没说明判断型测试本来就要由你判 |
| "判定无法验证"交出后由新的验证席位判，不由项目负责人判 | 项目负责人不能判断结果合不合格 |

### 16.5 统计与撤销
- 采纳率等统计只用于**提出建议**（例如"过去 30 次子卡批准你都原样采纳，是否交给项目负责人"），是否切换由你手动决定。
- 被代做的决定可以回看和撤销。撤销后的影响按"重开"处理：受影响的下游卡作废、重新验证，不受影响的保留（同 v5 1.10）。
