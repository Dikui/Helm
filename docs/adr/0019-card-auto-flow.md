# 卡片带自动流程，运行层推进机械步骤

按 ADR 0002 和 ADR 0017，调度者按事件唤醒，需要判断时才花模型上下文。执行完成后派出已确定的验收、全部通过后完成卡片，没有新的判断，逐步唤醒只增加时间和 token。把下一步作为可空的 `autoFlow` 数据保存在卡片上，由运行层复用 createDispatch 和 completeCard 的约束、事件与合并逻辑。

执行正常结束且自报完成后，运行层派出预写的验收票，以执行派单 id 和票序号组成幂等 key；不需验收的卡片直接完成。需要验收却没有预写票时仍交给调度者派单。最后一票结束后，只看当前提交未过期的已结束验收票，至少一票且全部正常通过才自动完成。自动完成后有卡片新就绪，或工作已无排队 / 运行派单时，以 card-completed 唤醒；其余成功步骤不唤醒。下游执行派单仍由调度者决定。

失败、受阻、未声明、异常结束或不全通过都沿用唤醒路径。自动派单或完成抛错时记录卡片的 auto-flow-stopped（步骤、错误 code 和 reason）并唤醒。只推进 executing 工作中未完成、未取消、未暂停的卡片，自动操作的 actor 为 runtime，调度笔记仍照常维护。

派单结束的事务只决定是否跳过唤醒，提交后再做异步派单或 git 合并。自动完成的状态、完成事件与必要的唤醒在同一事务提交，避免完成已记录但唤醒漏写。启动对账发现卡片没有活动派单，最新 dispatch-ended 后也没有新派单、完成或自动流程停止记录时，补该事件的唤醒，交调度者判断，不重放自动步骤。部分验收票已经创建时靠其排队 / 结束事件唤醒；预写的票尚未建齐时不自动完成，交回调度者处理。任务库仍是唯一权威状态，卡片详情和事件可见。

## Considered Options

- **调度者写 JS 编排**：长时间异步流程需要持久化和重放；脚本与卡片会有两份状态，重启、沙箱和执行权限都要新增约束，卡片图也难解释脚本走到了哪一步。
- **每一步都唤醒调度者**：语义简单，但已确定的机械步骤仍要重读简报并调用同样的工具。
- **自动多数决、返工或派下游执行**：不通过的事实需要判断，返工和下游执行内容也未预写，保留给调度者。
