# 验收派单各用一份固定提交的一次性副本，同一卡片的验收可以并行

原来同一张卡片同一时刻只允许一个派单，验收在卡片副本里跑，结束后把副本重置回开始时的提交。调度者对高风险卡片派 2–3 票交叉验收时，这几票只能排队，白白多等。用户 2026-10-25 决定让同一卡片的验收并行，做法与 pstack、software factory 和 Claude Code dynamic workflow 相同：验收的对象是一个固定的提交，每个验收者各拿一份这个提交的一次性副本。

- 派单时固定提交，记在派单的 `start_commit`：派过执行单的卡片取卡片分支末端，只验收的卡片取工作分支末端。在派单时而不是启动时固定，是为了让同一批验收看到同一版代码，即使并发上限让它们先后启动。
- 开始时用 `git worktree add --detach` 在 `worktrees/<工作>/verifications/<派单>` 开副本，没有分支，验收者改不到卡片分支和卡片副本。结束时先清进程，再删目录并 `git worktree prune`；启动对账删除整个 `verifications/`。
- 执行派单仍独占卡片：有执行派单时不能再派任何派单，有验收派单时不能派执行单。数据库唯一索引只约束执行派单，验收之间的并行由代码检查放开。
- 读派单时，验收派单带 `outdated`：卡片当前要验收的提交已不是它检查的那个。标记完成时，最近一次验收必须针对当前提交，否则拒绝（`VERIFICATION_OUTDATED`）。

代价：一次性副本里没有忽略文件（`node_modules`、构建缓存），验收者要自己装依赖。

## Considered Options

- **维持串行，只缩短排队**：不解决多票验收的等待。
- **多票共用卡片副本、分子目录**：测试、端口和进程仍会互相干扰，清理时也分不清是哪一票的。
- **启动时才固定提交**：并发上限让一批验收先后启动时，中途合入的上游会让它们看到不同的代码。
