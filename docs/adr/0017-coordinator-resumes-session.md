# 调度者在上下文变大前续跑同一会话

[ADR 0002](0002-task-based-coordinator.md) 让调度者每轮新开会话。2026-10-30 统计 15 轮 Claude 调度者：每轮首个请求只命中 1–2 万 token 的固定前缀，其余 4.7–10.8 万 token 每轮都重新写缓存；相邻轮次间隔全在 1 小时内（订阅缓存 TTL 为 1 小时），一轮内上下文平均只涨约 2.5 万。真实 CLI 实测 Claude（SDK `resume`）和 Codex（新进程 `thread/resume`，`CODEX_SQLITE_HOME` 每轮不同也能续）都能续跑同一会话，续跑时换掉 helm MCP 的轮次令牌即生效，模型记得上一轮内容，续跑后几乎全部命中缓存。用户 2026-10-30 决定：调度者续跑上一轮的会话，上下文大了就换新会话。

运行层在每轮结束时记下驱动报告的上下文占用（Claude 取最后一次主会话请求的输入加输出和 `modelUsage` 的窗口，Codex 取 `thread/tokenUsage/updated` 的 `last` 和 `modelContextWindow`）。下一轮只在上一轮正常结束、有会话、占用已知且低于 min(15 万, 窗口一半)、本轮没有压缩、调度者 Agent 快照（模型、提示词、规则、skills、MCP）不变时续跑，否则照旧新开。阈值按成本而不是窗口：opus 窗口 100 万，但每轮多次请求都要重读整段上下文，按缓存读 0.1 倍、写 1.25 倍估算，约 20 万占用时续跑就不比新开便宜。换会话不另写交接：调度笔记每轮照常整份改写，新会话读完整简报接上。续跑失败（会话文件丢失等）按本轮失败处理，下一轮自然新开。不报告占用的驱动（目前的 ACP 驱动）始终新开，以后接入的驱动报告了占用才续跑。

续跑的简报只带变化：去掉工作说明和调度笔记，新事件不含上一轮调度者自己的操作；卡片图、未决关卡、最近对话和唤醒事件照旧给出，标 `resumed: true`。

## Considered Options

- **保持每轮新开，只调简报顺序蹭缓存**：简报前半段（工作说明、卡片图）每轮会变，能蹭到的有限，每轮仍要重写大半缓存。
- **按窗口比例换会话（如 50%）**：opus 要到 50 万才换，那时一轮光缓存读取就上百万 token，比新开贵得多。
- **关掉 CLI 自动压缩、由 Helm 管理**：Codex 关不掉，且阈值远低于各家压缩点，压缩只作兜底；发生压缩时下一轮新开，因为摘要会丢细节。
- **空闲超过 1 小时（缓存过期）就新开**：实测数据里没有这种间隔，先不加；等关卡隔夜决定的情况多了再看。
