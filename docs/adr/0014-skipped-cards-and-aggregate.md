# 上游取消或撤回时下游卡片派生为"已跳过"，汇总卡片例外

原来上游卡片取消或关卡撤回后，下游永远停在"等待前置"，只能靠调度者记得删依赖；锦标赛里取消落败卡片会让依赖全部卡片的整体验收永远等不到。用户 2026-10-29 决定照 GitHub Actions、Airflow 的 skipped：上游卡片已取消、关卡已撤回或上游已跳过时，下游卡片为"已跳过"（`skipped`），沿依赖传递，不从图上删除、不能派单，审核和完成判断与已取消同样不算必需。

"已跳过"是 `refreshCardReadiness` 按当前依赖算出的派生状态，不是终态：删掉致因依赖或改依赖新的上游即恢复为等待前置 / 可派单，误取消可以挽回，不另设恢复操作。卡片带"汇总"标记（`aggregate`，整体验收、合成、比较三种依赖全部上游的卡片由调度者设置），汇总卡片把已取消、撤回、跳过的上游视为已结束，只等其余上游完成，全部上游都没了才跳过——对应 GitHub Actions 的 `if: always()`。

## Considered Options

- **已取消、已撤回视为已满足**：一行改动，但下游会在缺少上游成果时变成可派单，界面上也看不出哪些卡片已无意义。
- **取消或撤回时自动删除相关依赖**：效果相同，但卡片图上看不到原来的依赖关系。
- **维持等待，只在唤醒事件里列出受影响下游**：仍靠调度者记得处理。
