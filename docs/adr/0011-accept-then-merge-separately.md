# 审核接受只记录决定，合入和推送由用户分别操作；冲突交调度者解决，不重新审核

原来点"接受"就立刻把工作分支合进基准分支并推送，误点无法回退；合并冲突时只发一条提示，工作却标成已完成。用户 2026-10-28 决定照 GitHub PR 的做法拆开：接受只记录决定，工作进入待合入，合入前可以撤回；"合入"和"推送"是两个单独的操作。同一项目的合入由运行层串行执行，每次都用 `git merge-tree` 基于最新基准预检，所以后合入的工作负责解决与先合入的冲突。

冲突时工作停在待合入，用户二选一：

- **交给调度者**：运行层记下固定的基准提交，唤醒调度者派冲突卡片。运行层在卡片副本里预备好与该基准的合并，执行者只改文件、不自己 merge 或 commit，派单正常结束时由运行层保存合并提交；冲突卡片必须验收。完成后回到待合入，界面给出解决冲突产生的改动，不重新审核，原接受决定保留。
- **自己处理**：用户在本地合并后点重新检测，运行层只检查祖先关系，基准已包含工作分支就记为已合入，推送仍需单独点。

## Considered Options

- **接受即合入推送，误点用 revert 撤销**：撤销要再推一次 revert，基准分支历史留下噪音；推送出去的内容可能已被别人拉走。
- **解决冲突后重新审核**：冲突解决只改合并结果、且已强制验收，再走一遍审核让用户重看整份报告，代价大于收益。
- **执行者自己在副本里 git merge**：执行者沙箱里不能提交（Codex），且容易合错基准；由运行层固定基准、预备合并更可控。
