# 审核接受只记录决定，合入和推送由用户分别操作；冲突交调度者解决，不重新审核

原来点"接受"就立刻把工作分支合进基准分支并推送，误点无法回退；合并冲突时只发一条提示，工作却标成已完成。用户 2026-10-28 决定照 GitHub PR 的做法拆开：接受只记录决定，工作进入待合入，合入前可以撤回；"合入"和"推送"是两个单独的操作。同一项目的合入由运行层串行执行，每次都用 `git merge-tree` 基于最新基准预检，所以后合入的工作负责解决与先合入的冲突。

冲突时工作停在待合入，用户二选一：

- **交给调度者**：运行层记下固定的基准提交，唤醒调度者派冲突卡片。运行层在卡片副本里预备好与该基准的合并，执行者只改文件、不自己 merge 或 commit，派单正常结束时由运行层保存合并提交；冲突卡片必须验收。完成后回到待合入，界面给出解决冲突产生的改动，不重新审核，原接受决定保留。
- **自己处理**：用户在本地合并后点重新检测，运行层只检查祖先关系，基准已包含工作分支就记为已合入，推送仍需单独点。

## Considered Options

- **接受即合入推送，误点用 revert 撤销**：撤销要再推一次 revert，基准分支历史留下噪音；推送出去的内容可能已被别人拉走。
- **解决冲突后重新审核**：冲突解决只改合并结果、且已强制验收，再走一遍审核让用户重看整份报告，代价大于收益。
- **执行者自己在副本里 git merge**：执行者沙箱里不能提交（Codex），且容易合错基准；由运行层固定基准、预备合并更可控。


## 2026-10-29：合入即完成，推送可选，可结束不合入

本段取代上文中“已合入仍等待推送”的完成语义；接受与合入分开、冲突解决的决定继续有效。合入结果为 `merged` 或 `already-contained`（包括自己处理后重新检测）时，工作直接进入 `completed`，与合入结果在同一事务记 `work-completed`，清空暂停来源和运行暂停原因，然后清理工作副本、压缩输出。无需远端仓库也能完成交付。

移除工作状态 `merged`、`pushing`，它们仅在历史记录中保留；迁移将这些工作转为 `completed` 并补完成事件。旧 `pushing` 追加失败推送结果，说明运行层重启、中断后可重试。完成后的启动对账继续清理副本和压缩输出，绝不调用推送。

`push-work` 仅供已完成且合入结果成功或已包含的工作使用。推送只记 `base-push-result`，不改变工作状态，成功后隐藏按钮；失败和超时可重试。只读操作 `get-work-push-preview` 按本地远端跟踪 ref 列出基准分支的短 hash 和标题，包括本工作之外的本地提交；不访问网络，远端状态以最近 fetch 为准。预览与推送共用远端和目标分支选择，沿用基准分支的 upstream 配置；未配置时使用 origin 或唯一远端。无远端显示原因，缺失跟踪 ref 时说明将新建远端分支。实际推送限时两分钟，超时终止推送进程组（包括 hooks 和凭据助手），记失败结果。

用户在接受后、尚未合入时可确认“结束（不合入）”（`finish-work-without-merge`，仅用户可调用），包括合入冲突待处理及调度者正在解决冲突的情况。运行层先记完成以阻止新操作，停止轮次和派单后再清理副本与压缩输出。运行层记 `work-completed` 并注明 `withoutMerge: true`，删除工作副本、压缩输出，保留工作分支和审核记录；该完成方式不能再推送。

保留“推送成功才完成”的方案被否决：无远端时永远不能完成，调研类已包含工作也被迫推送，输出无法压缩。推送是整个基准分支的操作，因此完成与推送解耦，并在推送前展示全部待推送提交。
