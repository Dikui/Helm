# 调度者在自己的调度者目录里运行，取代"调度者对代码只读"

> 2026-11-03：调度者仍在调度者目录运行，但“只能写调度者目录”已被 [ADR 0026](0026-agents-run-without-sandbox.md) 取代：调度者无沙箱，改代码交给卡片是提示词约定。

去掉只读卡片（ADR 0023）后，调度者是 Helm 最后一处依赖 CLI 只读模式的地方，Grok 也因此不能当调度者。2026-11-02 决定：调度者的工作目录换成 Helm 数据目录下的 `coordinator/<工作>/`，同一工作所有轮次复用（续跑要求工作目录不变），工作结束时删除；权限与执行者相同，只能写这个目录、可联网、凭据禁读。四家 CLI 共同支持的写入模式都是"只能写当前工作目录"，所以要让调度者有可写处又写不了项目，只能把工作目录放到项目之外。硬约束随之改为"调度者只能写调度者目录"，改不了代码靠可写范围保证，而不是只读模式。代价是项目里的 `AGENTS.md`、`CLAUDE.md` 不再被 CLI 自动加载：简报列出这些说明文件的路径，调度者新会话先读一遍。调度者需要交付到项目的内容（如 ADR）仍走卡片副本卡片，经审核合入。

## Considered Options

- **保留只读沙箱**：Grok 的只读沙箱在 docker.sock 是软链接的机器上起不来，Codex 调度者不能联网。
- **工作目录仍是项目，另外放行写一个目录**：保留说明文件的自动加载，但 Grok 的 workspace profile 固定允许写工作目录，DeepSeek 的权限模式只有只读和可写工作目录两档，配不出来。
- **放开工作目录写入，合并时挑掉一部分**：没有工作副本时调度者就在用户的项目检出里写；有工作副本时会和卡片合并抢同一个工作区；也没有可靠规则区分谁写了什么。用户关心的是多个工作之间不冲突，单独目录在三种冲突（跨工作、与卡片合并、与用户改动）里都不冲突。
- **给调度者开副本，运行层把它的改动提交进工作分支**：可行且经审核，但要放弃按需开副本（ADR 0018），还要处理合并与写入的时序，而调度者本身并不需要往项目里写。
