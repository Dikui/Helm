## Question

调度者由谁来当（哪个模型、通过哪个 CLI 或 SDK 运行）？哪些事件会唤醒它，一项工作期间怎么常驻，什么时候退出？上下文快满了怎么交接给新会话？按工作类型加载哪些技能，从哪里加载？

## Comments

- 来自 01（2026-10-21）：用户选定调度者为**长时对话**（每项工作一个调度者会话，从对齐到审核），参照 Agent Teams、Factory；未采用 [17](17-coordinator-runtime-form-research.md) 的"短回合"。本单待定：① 上下文满了怎么办：CLI 自动压缩，还是先写外部记忆再换新会话（Anthropic 研究系统做法）；用户不想因压缩丢信息，倾向后者。② 两次唤醒之间进程常驻，还是退出后按 session id 续跑。调度者会话与执行者"每次派单起一个进程"差别很大，需单独设计。

- 2026-10-21 来自 [04](04-tech-stack.md)：调度者与执行者用同一套驱动（Claude Agent SDK、`codex app-server`、通用 ACP）；`codex exec`、`claude -p`、`grok -p` 这类一次性命令跑完即退出，不能当长时调度者，zcode 这类只有一次性命令的 agent 只能当执行者。会话是长时的；两次唤醒之间进程是否常驻、上下文满了怎么换会话，仍由本单决定。ACP 和 Claude SDK 下，调度者正在一轮里时，用户的新消息要排到下一轮或先取消再重发；只有 Codex app-server 能 `turn/steer` 插进当前轮。

- 来自 [05](05-task-store-model.md)（2026-10-21）：运行层唤醒调度者的事件：卡片变为待派单、派单结束、用户发来消息、关卡有了决定（含审核退回）、上游被取消或撤回导致下游卡住。工作暂停期间只投递用户消息，其余攒到恢复后。调度者会话作为实体入库（模板、对话 id、起止、结束原因），一项工作先后可有多个。

- 2026-10-22 冲突复核：调度者的驱动选择依赖 [22](22-driver-and-subscription-trial.md) 的实测结果（Claude SDK 是否扣订阅、Codex app-server 登录与并发、Grok 取消），本单排在 22 之后。

## Answer

2026-10-22 与用户讨论定稿。**推翻 [01](01-core-concepts.md) 的"长时对话"**：用户担心长时会话受上下文所限，改为任务型（即 [17](17-coordinator-runtime-form-research.md) 当时建议的"短回合"）。

1. **形态：任务型调度者**。每次唤醒新开一个 CLI 会话，读运行层拼好的启动简报，处理完这批事件就退出；不续跑上一轮的会话，不保留进程。一次唤醒叫一个**调度轮次**。平常的唤醒和崩溃后接续走同一条路径。代价是每轮重读简报、多花额度和几秒冷启动，用户接受（反目标里"多花时间或额度不算失败"）。对驱动不再要求长时会话。
2. **模板**：v1 建 Claude Code、Codex 两个调度者模板，默认 Claude Code；新建工作时可选另一个，轮次之间也可换。提示词、技能、MCP 只来自模板，由用户定制；Helm 带一份官方默认的"做软件项目"配置作为起点。不读 `~/.claude`、`~/.codex` 等本机全局配置（Claude SDK `settingSources: []`）。按工作类型加载技能 = 选不同模板，v1 只有一个。
3. **事件投递**：唤醒事件（见 05）进入该工作的队列；没有轮次在跑时，把攒下的事件合成一轮投递，每条只写"什么事 + 指向哪张卡片或哪次派单"，详情由调度者用工具读。同一工作同一时刻最多一个轮次。不用 Codex `turn/steer`。
4. **用户插话**：默认排队到下一轮。界面提供"打断"：取消当前轮次，立即开新一轮，被取消轮次的事件连同用户消息一起重投；打断不算失败。
5. **单轮内上下文满**：不专门设计。轮内保留 CLI 默认自动压缩兜底；驱动能发压缩通知的（Claude `compact_boundary`、Codex `contextCompaction`、Grok `auto_compact_started`）记一条事件，挂在该轮次下。溢出报错按第 6 条处理。各驱动读占用、关压缩的能力见 [context-usage-and-compaction.md](../../../docs/research/context-usage-and-compaction.md)，暂不使用。
6. **一轮失败**（崩溃、出错退出、超时、上下文溢出）：轮次正常结束，运行层才把这轮投递的事件标为已处理；失败则开新一轮重投，并附"上一轮中断，期间已做的操作见任务库"。调度者工具须可安全重复执行（派单幂等键、建卡前查状态），由 [07](07-hard-constraints-and-tools.md) 落实。看门狗同执行者：每轮总时长默认 30 分钟、无输出 10 分钟，可调。连续失败 3 次，暂停该工作并在对话里发运行层消息。
7. **启动简报**，由运行层每轮拼装：① 工作说明（对齐阶段为草稿并标"未确认"）；② 卡片图摘要，每卡一行：状态、依赖、执行者、最近一次派单的结束方式和自报结论；③ 未决决策关卡；④ 调度笔记全文；⑤ 上一轮以来的新事件；⑥ 对话（用户与调度者之间的消息和关卡，不含执行者输出）最近 20 条，更早的用工具读。派单完整最终回答、成果、日志不进简报，按需读。
8. **调度笔记**：每项工作一份，调度者每轮用工具整份改写（计划、判断、下一步、看过代码的要点），每个版本记一条事件；提示词要求控制在约 4k token，运行层不截断。
9. **何时停止唤醒**：工作审核通过或被取消后不再唤醒；暂停期间只投用户消息（同 05）。
10. **术语**（决策另记 [ADR 0002](../../../docs/adr/0002-task-based-coordinator.md)）："调度者会话"改为**调度轮次**（入库记所属工作、模板、CLI 会话 id、起止、触发事件、结束原因），"对话"不再对应任何 CLI 会话，新增"调度笔记"，已改 [GLOSSARY.md](../../../GLOSSARY.md)。

**待验证**（交 [14](14-coordinator-trial.md)）：任务型调度者跨轮次不失忆，即不重复派单、不忘记与用户商定的结论，对齐阶段一问一答的体验可接受。推翻时退到混合形态：对齐阶段按 CLI 会话 id 续跑，确认工作说明后改任务型。

- 2026-10-22 15 张整体复查：修订第 2 条。"只用模板配置、不读本机全局配置"扩展到**执行者**：用户的 `~/.claude/CLAUDE.md` 写的是手动调度时派 Codex、Grok 的规则，执行者读到会再派 agent，绕开并发上限和记录；08 实测 Grok 会加载全局 hook；Codex 会读 `~/.codex/config.toml`、`~/.codex/AGENTS.md`。Claude 用 `settingSources: []`；Codex 的登录也在 `CODEX_HOME`，"不读全局配置"能否做到（如单独 `CODEX_HOME` 只链接登录文件）、Grok 能否不加载全局 hook，交 [14](14-coordinator-trial.md) 验证，做不到的一家在模板说明里写明会继承哪些全局配置。另：Claude 调度者的只读不能只靠"关写工具"，Bash 仍能写 `_work`；须打开 SDK 沙箱且不把 `_work` 设为可写，做不到就不给 Bash，只留 Read/Grep/Glob。

- 2026-10-22 来自 [11](11-persistence-and-recovery.md)：helmd 重启时运行中的轮次记为结束（原因"运行层重启"），事件照常重投，但不计入"连续失败 3 次"，避免用户连续重启 helmd 时误暂停工作。

- 2026-10-22 交接前复查：修订第 6 条。调度轮次以"额度用完"结束时（调度者自己的额度用光），运行层直接暂停该工作，不重投、不等连败 3 次。由运行层暂停的两种情况（额度用完、连续失败 3 次）都列入 [15](15-v1-slice.md) 的待处理事项接口，并经 SSE 推送"需要用户处理"事件；额度恢复后由用户手动恢复，不做定时唤醒。执行者额度用完照旧由调度者改派；没有别家可派时，提示词要求调度者提决策关卡。
