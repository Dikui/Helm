## Answer

2026-10-22 grilling 定稿。顺带决定了地图"待明确"中的通知和额度两项。

**第一版范围**
- 驱动：调度者和执行者都用 Claude Agent SDK。
- 不做界面：用一个薄的 `helm` 命令行程序，通过 HTTP 接口发消息、看对话、决定关卡、看卡片和派单。界面依赖用户的前端设计，放在第三阶段，v1 是否做完以界面为准。
- 浏览器验收（09 的 Playwright MCP）进第一版。

**通知**：运行层只提供接口。出现待用户决定的关卡、工作进入审核时，经 SSE 推送"需要用户处理"事件，另有一个接口列出当前所有待用户处理的事项，放在第一版骨架里。怎么提醒用户归前端设计待办。系统通知命令、推送到手机不做（范围外）。

**额度与用量**（调研见 [usage-tracking.md](../../../docs/research/usage-tracking.md)）：每次派单和调度轮次都记录驱动报告的 token 用量，汇总到卡片和工作上，跟各驱动一起做。数据来源：Claude 用 result 消息的 `modelUsage`；Codex 用 `thread/tokenUsage/updated` 的 `total`；Grok 用 `session/prompt` 返回值 `_meta.usage`；DeepSeek 在派单结束后按会话 id 读取 `~/.dsh/sessions/.../session.v4.jsonl.zstd`，累加每步的 `usage`（内部格式，冒烟测试要覆盖）。不在派单前查额度。撞上限额时，驱动把它识别为结束方式"额度用完"，由调度者按提示词改派到别家。账户剩余百分比和美元花费不做（范围外）：前者是 Helm 和其他用途共用的，后者只是按标价估算。

**验证分三层**
1. 运行层逻辑用假驱动跑自动测试。假驱动按脚本回放预先写好的 agent 输出，接口和真实驱动一样，覆盖依赖、并发、关卡、`key` 去重、对账、合并冲突等，不消耗额度。
2. 每个真实驱动各有一组冒烟测试；原 14 的技术验证①～⑥作为对应阶段的验收项，用真实 CLI 跑（见本单 Comments）。
3. 端到端：网页版 2048，拆成 4～5 张有依赖关系的卡片（游戏逻辑、渲染、计分和存档、重开按钮等），其中两张卡片改同一个文件，故意造成合并冲突，用来练习修复卡片。第一版跑一次，包括浏览器验收；界面做完后再跑一次，由用户判断成功标准 6。

**开发顺序**

第一版（除第 7、8 步外都用假驱动测）：
1. 骨架：helmd 进程、SQLite（状态表加事件表）、由一份操作定义同时生成 HTTP 路由和 MCP 工具、SSE、通知接口、`helm` 命令行骨架
2. 驱动接口和假驱动
3. 执行派单：卡片副本（worktree）、并发上限、看门狗、`提交结论`工具、派单结束时提交、清理副本里的进程
4. 调度轮次：唤醒和事件合并、启动简报、轮次令牌、调度者工具（建卡、依赖、派单、标完成、关卡）、`key` 去重、连败 3 次暂停
5. 验收派单与合并：验收结束后重置副本、浏览器验收、合进工作分支、审核关卡、用 `merge-tree` 预检后合进基准分支
6. 启动对账与崩溃恢复
7. Claude 驱动：技术验证①②③⑤、token 记录、"额度用完"结束方式
8. 默认调度者提示词，用 2048 跑端到端

第二阶段：Codex 驱动（验证④⑥、token 记录、额度用完）、用户级服务自启动、输出管理（10 GB 提示、导出和删除）、换调度者模板。

第三阶段：界面（前置条件是用户的前端设计）、Grok 和 DeepSeek 驱动（ACP，含 token 记录），这两部分可以并行；最后用 2048 再跑一次端到端。

调度者能力（A1、A2）不在任何阶段的验收里，第一版只要求默认提示词能跑通完整流程。

- 2026-10-22 交接前复查：
  1. **`helm` 命令行**：子命令由操作定义生成，覆盖所有用户能用的操作（含暂停、恢复、取消、打断），不逐个列举；界面做好后保留。第一版还用它登记项目和设并发上限。
  2. **Agent 模板**：第一版内置两个默认模板（Claude 调度者、Claude 执行者），不支持新增或修改；模板管理与第二阶段的"换调度者模板"一起做。
  3. **通知补一类**：工作被运行层暂停（调度者额度用完、连续失败 3 次）也列入待处理事项并推送"需要用户处理"；调度轮次额度用完直接暂停，不重投（见 [06](06-coordinator-lifecycle.md) 的复查评论）。执行者额度用完、没有别家可派时，提示词要求调度者提关卡。
  4. **2048 端到端不强求合并冲突**：拆单由调度者决定，保证不了。冲突和修复卡片的流程由假驱动自动测试覆盖；端到端里出现了就顺带检查。
  5. **开发测试省额度**（用户要求）：真实驱动的冒烟测试和端到端测试都用消耗小的模型、调低推理强度。默认模板因此要能设模型和推理强度。
