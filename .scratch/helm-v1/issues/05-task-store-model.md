## Question

任务库里存什么：工作、工作说明、卡片、依赖、派单与派单结果、消息、事件、验收结果、用户决定。各自有哪些状态，怎样流转？怎样保证每个问题都能追溯到具体的 agent 和步骤？

## Answer

2026-10-21 grilling 定稿。术语见 [GLOSSARY.md](../../../GLOSSARY.md)，存储方式见 [ADR 0001](../../../docs/adr/0001-state-tables-plus-event-log.md)。具体表结构到实现阶段再定。

**存储与追溯**
- 当前状态表 + 事件表，每次操作在同一事务里改状态、写事件；状态只由运行层根据操作和进程信号改写，模型不直接写。不做纯事件溯源，也不用文本日志。
- 事件记录时间、执行者（用户 / 调度者会话 / 派单 / 运行层）、对象、动作、细节，不记因果链。"步骤"是派单输出和调度者会话输出中的序号；两种输出按序号存成库外文件，库里只记路径。

**实体**

| 实体 | 主要内容 | 状态 |
|---|---|---|
| 项目、Agent 模板 | 用户登记的配置，与其他实体同库 | — |
| 工作 | 所属项目、当前生效的工作说明版本 | 对齐中 / 执行中 / 待审核 / 已完成 / 已暂停 / 已取消 |
| 工作说明版本 | 需求、边界、标准、版本号、确认它的关卡 | 草稿 / 已生效 / 已被取代 |
| 卡片 | 内容、是否需要验收、修复自哪张卡片（可空） | 等待前置 / 待派单 / 执行中 / 验收中 / 已暂停 / 完成 / 已取消 |
| 决策关卡 | 种类（一般 / 确认工作说明 / 审核）、创建方（调度者 / 运行层）、问题、正文、可选项、用户的决定（选项或自由回答、意见、时间）、撤回原因 | 等待决定 / 已决定 / 已撤回 |
| 依赖 | 节点 → 节点，节点是卡片或决策关卡 | — |
| 派单 | 所属卡片、用途（执行 / 验收）、执行者模板、执行者对话 id、验收依据的工作说明版本；派单结果：结束方式（正常完成 / 出错退出 / 超时终止 / 被中止+原因）、最终回答、自报结论（完成 / 受阻，通过 / 不通过，未声明） | 排队中 / 运行中 / 已结束 |
| 成果 | 所属派单、种类（分支 / 文件 / 测试输出）、路径或 ref | — |
| 调度者会话 | 所属工作、模板、对话 id、起止时间、结束原因；一项工作先后可有多个 | 运行中 / 已结束 |
| 消息 | 所属工作、发送方（用户 / 调度者）、关于哪张卡片或哪个关卡、正文、送达调度者的时间；写入后不再修改 | — |
| 事件 | 见上 | 只追加 |

**交互**
- 每项工作一条对话，由消息和决策关卡按时间穿插组成，对应调度者会话。用户看到的四种交互（普通消息、决策关卡、确认工作说明、审核）底层相同，区别只在发起方和是否阻塞。消息是"说过的话"，不可改；关卡是有状态、可修改、被依赖的对象，问题和正文的每次修改记成事件，所以两者分开存。
- 只有用户的决定能关闭关卡。调度者可以撤回自己提出的一般关卡，也可以撤回工作说明修改后提出的确认关卡；开头由运行层自动生成的"确认工作说明"和审核关卡是固定关卡，不能撤回。
- 审核关卡的正文就是汇总报告，可选项固定为接受 / 退回；退回后旧关卡保留，调度者处理完再发起新的审核关卡。
- 执行者不能提关卡，只能在最终回答里自报"受阻"，由调度者决定自己处理还是提关卡。

**状态规则**
- 工作："对齐中"只看开头那个确认关卡；待审核 = 有未关闭的审核关卡；退回后回到执行中。"等待用户"不是状态，由未关闭的关卡推导。
- 卡片：等待前置 / 待派单由依赖推导（待派单 = 前置满足且从未派单）；执行中 / 验收中看最近一次派单的用途，两次派单之间保持不变。完成由调度者标记，需要验收的卡片须最近一次验收派单为"通过"。完成和已取消都是终态，返工时新建修复卡片并注明修复自哪张。已暂停只由用户设置和恢复。
- 派单：并发满时排队，不拒绝（07 可以推翻）。"被中止"的原因：卡片暂停、卡片取消、工作暂停、工作取消、调度者撤销。
- 依赖：不预先派单；调度者在卡片变为待派单后派单，可以把上游结果写进派单。上游卡片完成、上游关卡已决定，下游才解除阻塞；上游被取消或撤回时，下游保持阻塞并唤醒调度者，运行层不自动放行，也不连锁取消。
- 暂停卡片：中止它正在运行的派单，拒绝新派单，恢复后由调度者重新派单（可以续跑同一对话）。暂停工作：不改卡片状态，中止该工作所有派单，拒绝新派单，暂缓投递自动唤醒；用户的消息仍会唤醒调度者，用户仍可对关卡作决定。
- 工作说明分版本、只读，确认后才生效；修改时由调度者起草、提确认关卡，默认不阻塞正在运行的卡片。验收以生效的最新版本为依据，并记在验收派单上。
- 整项工作验收：调度者建一张"整体验收"卡片，依赖所有其他卡片，它的派单都是验收派单。

**交给后续任务单**：唤醒事件清单 → 06；硬约束清单与拒绝方式 → 07；worktree、分支、合并状态 → 08；自报结论格式、整体验收卡片 → 09；交互界面与提醒 → 10、12；输出保留策略 → 11。已在各单留评论。

- 2026-10-22 来自 [06](06-coordinator-lifecycle.md)：实体"调度者会话"改为**调度轮次**（所属工作、模板、CLI 会话 id、起止、触发事件、结束原因；状态 运行中 / 已结束），一次唤醒一个，同一工作同时最多一个。新增实体**调度笔记**：每项工作一份，调度者每轮整份改写，每个版本记一条事件。事件的执行者"调度者会话"改为"调度轮次"；"对话对应调度者会话"一句作废。轮次投递的事件在轮次正常结束后才标为已处理。

- 2026-10-22 15 张整体复查：① 卡片完成条件放宽：从没正常完成过**任何**派单（原为"执行派单"）的卡片不能标完成，需要验收的仍须最近一次验收通过。整体验收卡片因此就是一张普通卡片：需要验收、只派验收派单，不新增卡片种类。② 审核被接受后工作照常进入"已完成"，合并进基准分支和推送的结果记成事件，不新增工作状态（见 [08](08-isolation-and-merge.md) 的复查评论）。

- 2026-10-22 来自 [09](09-acceptance.md)：① 自报结论不再从最终回答解析，改由执行者调用 helmd 注入的 `提交结论` 工具给出（取值不变，另附一句理由），没调用记为未声明。② 派单加字段：是否需要浏览器、分配的端口段；验收派单另记被验收的卡片分支提交 SHA 和卡片说明快照（工作说明版本照旧记录）。
