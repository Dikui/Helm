Map: [Helm v1 设计](../map.md)

## Question

Helm 里有哪些核心概念，各叫什么：工作（一次需求）、任务单、派单（一次执行尝试）、调度者、执行者、验收、审核、决策关卡……它们之间是什么关系？结果写进 `GLOSSARY.md`。尽量和 Olympus 架构里的叫法一致（卡片、派单、决策关卡），方便以后接入。

## Answer

2026-10-21 grilling 定稿，术语与定义见 [GLOSSARY.md](../../../GLOSSARY.md)，与 Olympus 的卡片、派单、消息、决策关卡保持一致。

- **层级**：项目（一个代码仓库）⊃ 工作 ⊃ 卡片图（卡片 + 依赖 + 决策关卡）⊃ 卡片 ⊃ 派单（执行派单 / 验收派单）。卡片不嵌套。
- **工作的首尾**：工作从**对齐**开始，产出**工作说明**（需求、边界、标准），用户确认后调度者拆卡片，卡片图不需要批准就开始执行；**审核**是最后一个决策关卡，由用户针对整项工作进行。卡片间的依赖由调度者确定，由运行层强制执行。
- **角色**：用户预先登记 **Agent 模板**（CLI、参数、配置、职责），每个模板的角色固定为调度者或执行者，一个模板可以实例化多份。每项工作有自己的**调度者**，以一个长时**调度者会话**运行（参照 Agent Teams、Factory，未采用 [17](17-coordinator-runtime-form-research.md) 的短回合）；执行者每次派单实例化一次。由调度者派单，不设领单。**运行层**不是 Agent，**任务库**属于运行层。
- **验收与打回**：验收由执行者通过验收派单在新上下文中完成，按卡片验收还是按整项工作验收由调度者决定；验收不通过即打回。
- **沟通**：**消息**由用户写在工作或卡片下，由调度者接收，本身不改变状态；**操作**才改变状态，并记成**事件**。用户中途修改时，由调度者判断冲突程度：不冲突就立即改；冲突但能等就记成待办；冲突太大就加决策关卡。暂停和取消由运行层直接执行。
- **记录**：**派单结果** = 结束方式（正常退出、出错退出、超时终止、被取消，由运行层判定）+ 执行者的最终回答（仅正常退出时有），调度者只读派单结果。**成果**由运行层保存，在界面上展示。实时状态由运行层根据事件推出。**汇总报告**只写结论和指向成果的链接。**派单输出**原样保存，工作结束后精简。依据见 [16](16-results-and-outputs-research.md)。
- **交给后续任务单**：上下文满了怎么办、进程是否常驻 → 06；验收派单的"通过 / 不通过"格式 → 09；中途修改的处理规则 → 10；派单输出的保留策略 → 11；长时对话下 A2 是否成立 → 14。v1 允许多项工作并行，并发上限仍放在 `Not yet specified`。
- 不建 ADR：这些都是术语和概念层面的决定，容易修改。
