# 持久化与崩溃恢复

Type: grilling
Status: resolved
Labels: wayfinder:grilling
Blocked by: 04, 05
Map: [Helm v1 设计](../map.md)

## Question

守护进程、调度者或执行者崩溃后，怎么恢复且不重复已完成的步骤？用 DBOS（SQLite）这类持久化执行库，还是自己写状态表加启动时扫描？等待用户审核时状态停在哪里？

## Comments

- 来自 01（2026-10-21）：派单输出很占空间，用户要求工作结束后加以整合，只保留重要信息；事件保留。保留什么、保留多久，由本单决定。

- 2026-10-21 来自 [04](04-tech-stack.md)：调度者和执行者都是 `helmd` 的子进程，`helmd` 重启时随之退出，不重新接管；恢复靠各驱动的续跑：Claude SDK `resume`、Codex `thread/resume`（读 `~/.codex/sessions` 的 rollout 文件，需用回原 `CODEX_SQLITE_HOME`）、ACP 按 `initialize` 能力选 `session/resume` 或 `session/load`，都没有就用 CLI 自己的 `--resume`。

- 来自 [05](05-task-store-model.md)（2026-10-21）：任务库为当前状态表 + 事件表、同事务写入（[ADR 0001](../../../docs/adr/0001-state-tables-plus-event-log.md)）。派单输出和调度者会话输出按序号存成库外文件，库里只记路径；保留多久由本单定。暂停是终止派单而非冻结进程，恢复时由调度者重新派单、续跑同一对话。

- 2026-10-22 冲突复核：派单输出和调度者会话输出不精简，推翻 01 的"工作结束后精简"。原样保存，工作结束后 gzip 压缩，不删内容。本单只需定一条提示条件（总量超过多少，或工作结束超过多少天），提示用户手动删除，不自动删。依据：本机 `~/.codex/sessions` 713 个会话中位数 2.6 MB、最大 32 MB，`~/.claude/projects` 127 个中位数 0.6 MB；一项工作估计 80–100 MB，压缩后约 10–20 MB。

- 2026-10-22 来自 [22](22-driver-and-subscription-trial.md)：续跑实测：Codex 在全新 sqlite 目录的新进程里 `thread/resume` 旧 thread 成功；Grok 新进程 `session/load`、`session/resume` 都成功。未确认：Grok `session/cancel` 后正在跑的子进程是否被杀，看门狗不能假设取消会清掉子进程。

- 2026-10-22 来自 [06](06-coordinator-lifecycle.md)：调度者改为任务型，崩溃恢复不再续跑 CLI 会话：轮次失败就开新一轮重投未处理事件，连续失败 3 次暂停工作并通知用户；helmd 重启后，运行中的轮次按失败处理。原"调度者会话输出"改称"调度轮次输出"，保存策略同派单输出。

- 2026-10-22 来自 [08](08-isolation-and-merge.md)：恢复时要处理 git 状态：执行派单中断后，卡片副本里可能有未提交的改动（helmd 只在派单正常结束时提交）；`_work` 里可能有一半的合并（中断时应 `merge --abort`）；还有终态卡片残留的 worktree 和分支（按 08 的规则补删）。worktree 在 `~/.helm/worktrees/`。

## Answer

2026-10-22 与用户讨论定稿。

1. **不用持久化执行库**（DBOS、Temporal 一类）。运行层没有可重放的长流程：编排交给调度者，运行层每个操作都是一个短事务加一个外部动作，耗时的执行者进程也没法设断点。沿用 05 的状态表加事件表，helmd 启动时做**启动对账**：对照任务库检查进程和 git 的实际状态，补做或回滚。理由补进 [ADR 0001](../../../docs/adr/0001-state-tables-plus-event-log.md)。
2. **外部动作先做、写库后做**。外部动作指库以外改变机器状态的操作（git 合并、删除 worktree、推送、拉起或杀进程），必须可以安全重做；它成功后才在同一事务里改状态、写事件。崩溃后最坏是"做了没记"，启动对账或调度者带同一 `key` 重试时补写：
   - 标记完成：先 `--no-ff` 合进工作分支再写"完成"，重试时合并为"已是最新"。
   - `_work` 里合并到一半：启动时 `merge --abort`。
   - 审核接受后合进基准分支并推送：工作"已完成"但缺合并或推送结果事件的，启动时补做；基准分支已包含工作分支就跳过合并；用户项目目录里留有 helmd 发起的、指向工作分支的 `MERGE_HEAD` 时先 `merge --abort` 再重做。
   - 终态卡片残留的 worktree、卡片分支，已结束工作残留的 `_work`：按 08 第 8 条补删。
3. **helmd 重启时运行中的派单**：记为"被中止，原因：运行层重启"，写事件唤醒调度者，由调度者决定续跑、新开或改派；运行层不自动续跑（修订 04）。拉起后、记下对话 id 前崩溃的派单只能新开。执行者已发结束消息但结果没入库的，同样按被中止处理，调度者续跑时由执行者自己发现已完成。排队中的派单保持排队，未处理的唤醒事件照常投递，已暂停的工作保持暂停。正常停止（升级、重启服务）与崩溃走同一路径，不等派单跑完。
4. **执行派单任何结束方式都提交**（08 第 3 条"每次执行派单结束后提交"本已涵盖，这里明确包括超时、出错退出、被中止）。提交信息写派单 id 和结束方式；因运行层重启而中断的，由启动对账补提交。提交前先删掉残留的 `index.lock`（此时相关进程已杀），并 abort 副本里进行中的 merge、rebase、cherry-pick、revert，记一条事件（实测见下方评论）。卡片副本在两次派单之间总是干净的，续跑的执行者能看到之前的进度，验收派单结束时的重置不会丢掉未提交改动。半成品不会被合进工作分支：标记完成仍需有一次派单正常完成。
5. **孤儿进程**（硬约束，已按实测修订）：启动时先杀进程，再动 git。① 工作目录在 `~/.helm/worktrees/` 下的所有进程，连同各自的进程组，一律杀掉，这能覆盖执行者、调度轮次及它们起的命令和后台服务。② helmd 拉起、工作目录不在副本里的进程组（09 的 Playwright MCP）在库里记 pgid 和启动时间，仍存活且组长启动时间对得上的杀整组，回收端口段。不依赖"管道断了子进程会自己退出"。用户自己的终端若停在副本目录里，也会被杀。用 `setsid` 并换走工作目录的进程查不到，不防。
6. **调度轮次**：helmd 重启时运行中的轮次记为结束（原因"运行层重启"），事件重投，不计入 06 的"连续失败 3 次"。
7. **等待审核**：审核关卡只是库里一行"等待决定"，没有进程在等，不设超时，重启不受影响。
8. **输出保留**（派单输出与调度轮次输出）：原样保存，工作结束后 gzip，不自动删。`~/.helm/` 下输出总量超过 10 GB（可调）时界面提示一次，不按天数提示。已结束的工作可在界面上"删除输出"：删除前提示先导出，并提供"导出"（默认导出为一个 `.tar.gz`，含该工作的全部输出文件和它在任务库里的记录 JSON，存到用户选的位置）。删除只删库外文件，库里的派单、事件保留，路径标为"已删除"。

**修订与交接**：04（重启后不自动续跑）、05（派单记 pgid 与启动时间、输出"已删除"标记、被中止原因加"运行层重启"）、06（重启不计失败）、08（任何结束都提交、启动对账补删补合）、12（存储提示、导出与删除输出按钮）已留评论；GLOSSARY "派单结果"、ADR 0001 已更新。

- 2026-10-22 实测（脚本 `.scratch/prototype/helm-recovery/`，未提交；macOS，git 2.54）：
  - **进程**：空闲的 `codex app-server`、`grok agent stdio`、`dsh --profile acp`、`claude` stream-json 在管道断开后都自己退出。但正在干活的执行者（`codex exec`、`claude -p`、`grok -p`）管道断开 5 秒后仍在运行，会继续写副本。Claude、Grok、Codex 都把每条 shell 命令放进**单独的进程组**，`nohup ... &` 起的后台进程挂到 launchd 下，所以只杀执行者的进程组时三家的命令全部残留。macOS 上 `ps -E` 读不到其他进程的环境变量，环境变量标记不可用。用 `lsof -d cwd` 按工作目录找，三家残留的命令全部找到并清掉。第 5 条据此修订。
  - **git**：同一卡片分支 `--no-ff` 合两次，第二次为 "Already up to date"，没有新提交；`_work` 留着 `MERGE_HEAD` 时 `merge --abort` 后干净；基准分支已包含工作分支时 `merge-base --is-ancestor` 判出并跳过；项目目录留有 `MERGE_HEAD` 时 abort 再合成功。三处需要修订：① 残留 `index.lock` 时提交直接失败，要先删锁。② 执行者合并到一半被杀时，`add -A` 加 commit 会把冲突标记当成合并结果提交。③ rebase 到一半时提交落在游离 HEAD 上、不在卡片分支里。所以提交前要先删锁并 abort 进行中的 git 操作，第 4 条据此修订。
  - **命名冲突**（08 的问题）：工作分支 `helm/<工作>` 与卡片分支 `helm/<工作>/<卡片>` 不能同时存在（git 报 `'refs/heads/helm/w' exists; cannot create 'refs/heads/helm/w/c1'`）。卡片分支改为 `helm-card/<工作>/<卡片>`，已在 08 留评论。
