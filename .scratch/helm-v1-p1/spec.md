# Helm v1 第一版

Status: ready-for-agent
Map: [Helm v1 设计](../helm-v1/map.md)

本文只覆盖 [15](../helm-v1/issues/15-v1-slice.md) 定的第一版：调度者和执行者都用 Claude Agent SDK 打通完整流程（含浏览器验收），用 `helm` 命令行代替界面，用网页版 2048 跑一次端到端。第二、三阶段见 Out of Scope。术语以 [GLOSSARY.md](../../GLOSSARY.md) 为准，架构决策见 [ADR 0001](../../docs/adr/0001-state-tables-plus-event-log.md)、[ADR 0002](../../docs/adr/0002-task-based-coordinator.md)、[ADR 0003](../../docs/adr/0003-own-sandboxes-and-work-branch.md)。各项决策的来由在地图的任务单里，本文只写结论。

## Problem Statement

用户现在靠 Claude Code 加一份全局 `CLAUDE.md` 手动调度多个 agent：要盯着终端，看不到每个 agent 做到哪一步，编排写死在提示词里，多个 agent 之间没有隔离，出了问题说不清是谁在哪一步做错的。用户离开电脑，工作就停了。

## Solution

用户在一个项目上用 `helm` 命令行发出一条消息，即开始一项工作。后台进程 `helmd` 为这项工作唤醒调度者，调度者和用户对齐出工作说明；用户确认后，调度者把工作拆成卡片和依赖，派给执行者。每个执行者在自己的卡片副本里、在自带的沙箱里并行工作，由另一次派单在新上下文里验收；卡片完成即合进工作分支。最后调度者写汇总报告发起审核，用户接受后 `helmd` 把工作分支合进基准分支并推送。

用户只在三种场合出场：确认工作说明、回答决策关卡、审核。其余时间不用盯终端，需要用户处理时 `helmd` 会通过 SSE 推送事件，也有接口列出全部待处理事项。每次操作、每次派单、每个调度轮次都记成事件，派单输出按步骤保存，任何问题都能追到具体的派单和步骤。

## User Stories

**项目与工作**

1. As a 用户, I want 用 `helm` 命令行登记一个本机 git 仓库为项目, so that Helm 可以在它上面开工作
2. As a 用户, I want 选一个项目、发第一条消息就新建一项工作, so that 我不用先填表单
3. As a 用户, I want 一个项目下同时有多项工作, so that 不相关的需求可以并行推进
4. As a 用户, I want 列出所有工作及其状态、是否有待我决定的关卡、是否被运行层暂停及原因, so that 我一眼知道哪里需要我
5. As a 用户, I want 设置全局执行者并发上限（默认 10）, so that 我能控制同时消耗的额度和机器资源
6. As a 用户, I want 看到当前执行者并发数、上限和排队数, so that 我知道为什么有派单在等

**对齐**

7. As a 用户, I want 工作新建时运行层自动生成"确认工作说明"关卡并唤醒调度者, so that 对齐马上开始
8. As a 用户, I want 调度者起草工作说明（需求、边界、标准），我只通过消息要求修改, so that 工作说明的每一版都有记录
9. As a 用户, I want 确认关卡同时展示工作说明、基准 ref（默认当前分支 HEAD）和未提交改动的提醒, so that 我知道工作从哪份代码开始
10. As a 用户, I want 确认后由 `helmd` 从基准 ref 开出工作分支 `helm/<工作>`, so that 我自己的分支在审核接受前不被动过
11. As a 用户, I want 确认后再改工作说明时由调度者起草新版本并提新的确认关卡, so that 只有我确认过的版本才生效

**对话与决策关卡**

12. As a 用户, I want 看到一项工作的对话：消息和关卡按时间穿插, so that 我能读懂调度者和我之间说过什么
13. As a 用户, I want 发消息时注明关于哪张卡片或哪个关卡, so that 调度者知道我在说什么
14. As a 用户, I want 对决策关卡选选项或写自由回答，也可以先在对话里追问, so that 我能在弄清楚后再决定
15. As a 用户, I want 关卡未决定前，它后面的卡片一律阻塞, so that 执行者不会在我拍板前开工
16. As a 用户, I want 我发的消息默认排到下一个调度轮次, so that 调度者当前一轮不被打乱
17. As a 用户, I want 打断当前调度轮次并立即开新一轮, so that 急事不用等
18. As a 用户, I want 用一个接口列出所有待我处理的事项，并在出现新事项时收到 SSE"需要用户处理"事件, so that 以后的界面或我自己的脚本能提醒我

**卡片图与派单**

19. As a 用户, I want 看到卡片图：每张卡片的状态、执行者模板、依赖和关卡节点, so that 我知道整体进度
20. As a 用户, I want 看到每张卡片做到哪一步（当前步骤号和最新一步的一行摘要，实时更新）, so that 不用打开派单输出就知道它在干什么
21. As a 用户, I want 看到每张卡片的全部派单及派单结果（结束方式、被中止的原因、自报结论及理由、最终回答、token 用量）, so that 我能判断卡片为什么成功或失败
22. As a 用户, I want 按步骤查看派单输出, so that 我能追到执行者内部的具体步骤
23. As a 用户, I want 看到卡片的成果（分支、文件、测试输出）, so that 我能直接检查产出
24. As a 用户, I want 暂停、恢复、取消卡片和工作, so that 方向错了能马上止损
25. As a 用户, I want 我不能直接标完成、建卡片、改依赖或派单，这些都通过消息交给调度者, so that 编排只有一个入口、都有记录
26. As a 用户, I want 卡片和工作汇总 token 用量, so that 我知道一项工作花了多少

**调度者**

27. As a 调度者, I want 每次被唤醒时拿到一份启动简报（工作说明、卡片图摘要、未决关卡、调度笔记、新事件、最近 20 条对话）, so that 我不依赖上一轮的上下文也能接着干
28. As a 调度者, I want 用工具读卡片详情、派单的完整最终回答、成果、派单输出、更早的对话、关卡修改历史和事件, so that 简报之外的细节按需取用
29. As a 调度者, I want 用工具建卡片、改卡片、设置是否需要验收、加删依赖、派单、撤销派单、标记完成、取消卡片, so that 我能推进卡片图
30. As a 调度者, I want 用工具起草工作说明、发消息、提出修改撤回一般关卡、发起审核, so that 我能和用户沟通
31. As a 调度者, I want 每轮整份改写调度笔记, so that 下一轮知道我的计划和判断
32. As a 调度者, I want 新建类工具带 `key`、重复调用返回已有对象, so that 一轮失败重投时不会重复建卡或派单
33. As a 调度者, I want 违反约束时工具当场返回错误码、原因和当前允许的操作, so that 我能自己纠正
34. As a 调度者, I want 标记完成时卡片分支与工作分支冲突就被拒绝、卡片状态不变, so that 我新建修复卡片去解决冲突
35. As a 调度者, I want 执行者额度用完时派单以"额度用完"结束, so that 我能改派别的执行者模板，没得改派时提关卡

**执行与验收**

36. As a 执行者, I want 只能在自己的卡片副本里写代码，副本外的写入被沙箱或权限拦下, so that 我不会弄坏用户项目或别的卡片
37. As a 执行者, I want 用唯一的 Helm 工具"提交结论"自报完成或受阻、通过或不通过并附理由, so that 结论不靠解析我的回答
38. As a 执行者, I want 拿到一段本机端口（通过环境变量）, so that 我起的开发服务不和别的派单冲突
39. As a 执行者, I want 派单标了"需要浏览器"时得到 `helmd` 转发的浏览器工具, so that 我能在沙箱里起服务、从沙箱外的浏览器检查页面
40. As a 验收者, I want 验收派单总是新开对话，内容前附卡片说明快照, so that 我在新上下文里按卡片说明检查
41. As a 用户, I want 验收派单结束后副本被重置到派单开始时的提交, so that 验收者改代码让自己通过的情况不会发生
42. As a 用户, I want 执行派单不论怎样结束，`helmd` 都把副本里的改动提交到卡片分支, so that 续跑的执行者能看到之前的进度
43. As a 用户, I want 执行者推送不到远端, so that 只有审核接受后的成果才会出现在远端

**审核**

44. As a 用户, I want 审核关卡的正文是汇总报告，逐张卡片写结果、验收是否通过、由谁完成，附成果链接, so that 我能判断这项工作能不能收
45. As a 用户, I want 审核旁固定附上工作分支相对基准 ref 的 diff、整体验收结论、被拒绝的操作数和未声明结论的派单数, so that 不依赖调度者写得准不准
46. As a 用户, I want 审核只有接受或退回加意见（意见可引用 `文件:行`）, so that 决定简单明确
47. As a 用户, I want 接受后 `helmd` 先预检、无冲突才合进基准分支并推送，冲突或推送失败只报告, so that 我的项目目录永远不会停在冲突状态
48. As a 用户, I want 退回后调度者处理完再发起新的审核, so that 每次审核都有自己的汇总报告

**恢复与可靠性**

49. As a 用户, I want `helmd` 重启后自动对账：杀掉残留进程、收拾半截的 git 操作、补做未记结果的合并与推送, so that 崩溃不会留下坏状态
50. As a 用户, I want 重启时正在运行的派单记为"被中止：运行层重启"并交调度者决定续跑、新开或改派, so that 不会有派单悄悄消失
51. As a 用户, I want 调度者连续失败 3 次或自己额度用完时工作被暂停并列入待处理事项, so that 工作不会悄悄停下
52. As a 用户, I want 每次派单和调度轮次结束时副本里的残留进程被结束, so that 后台程序不会占端口或在提交、重置之后改代码
53. As a 用户, I want 一份可按卡片、派单、执行方筛选的事件时间线, so that 任何问题都能追到具体的 agent 和步骤

**开发与验证**

54. As a 开发者, I want 一个按脚本回放 agent 输出的假驱动，接口和真实驱动一样, so that 运行层逻辑能确定地、不花额度地自动测试
55. As a 开发者, I want 内置模板能设模型和推理强度, so that 冒烟测试和端到端测试用消耗小的模型

## Implementation Decisions

### 进程与存储

- TypeScript，Node 22 或更高。每台机器一个 `helmd`，只监听 `127.0.0.1`，管理所有项目；第一版用前台 `helm serve` 启动。
- 任务库是 `~/.helm/helm.db`（`node:sqlite`，WAL，只有 `helmd` 写），派单输出、调度轮次输出和成果文件放在 `~/.helm/` 下的普通文件里，库里只记路径。
- 每次操作在同一事务里改当前状态行、追加一条事件（ADR 0001）。事件记时间、执行方（用户 / 调度轮次 / 派单 / 运行层）、对象、动作、细节，不记因果链。"步骤"是派单输出和调度轮次输出中的序号。
- 外部动作（git 合并、删 worktree、推送、拉起或杀进程）先做且可安全重做，成功后再写库。

### 实体与状态

具体表结构在实现时定，实体和状态按 [05](../helm-v1/issues/05-task-store-model.md)：

| 实体 | 要点 | 状态 |
|---|---|---|
| 项目 | 一个 git 仓库 | — |
| Agent 模板 | 第一版内置 Claude 调度者、Claude 执行者两个，只能设模型和推理强度 | — |
| 工作 | 所属项目、生效的工作说明版本、基准 ref、工作分支、`_work` 路径、运行层暂停原因 | 对齐中 / 执行中 / 待审核 / 已完成 / 已暂停 / 已取消 |
| 工作说明版本 | 需求、边界、标准、版本号、确认它的关卡 | 草稿 / 已生效 / 已被取代 |
| 卡片 | 内容、是否需要验收、修复自哪张卡片、副本路径、卡片分支 | 等待前置 / 待派单 / 执行中 / 验收中 / 已暂停 / 完成 / 已取消 |
| 决策关卡 | 种类（一般 / 确认工作说明 / 审核）、创建方、问题、正文、可选项、用户的决定、撤回原因 | 等待决定 / 已决定 / 已撤回 |
| 依赖 | 节点 → 节点，节点是卡片或决策关卡 | — |
| 派单 | 所属卡片、用途（执行 / 验收）、执行者模板、CLI 会话 id、是否需要浏览器、端口段、pgid 与启动时间、token 用量；验收派单另记被验收的提交 SHA、卡片说明快照、工作说明版本；派单结果（结束方式、最终回答、自报结论及理由） | 排队中 / 运行中 / 已结束 |
| 成果 | 所属派单、种类（分支 / 文件 / 测试输出）、路径或 ref；已完成卡片的分支成果指向工作分支上的合并提交 | — |
| 调度轮次 | 所属工作、模板、CLI 会话 id、起止、触发事件、结束原因、pgid 与启动时间、token 用量 | 运行中 / 已结束 |
| 调度笔记 | 每项工作一份，每个版本记一条事件 | — |
| 消息 | 发送方（用户 / 调度者 / 运行层）、关于哪张卡片或关卡、正文、送达调度轮次的时间；不可改 | — |
| 事件 | 见上 | 只追加 |

- 派单结束方式：正常完成 / 出错退出 / 额度用完 / 超时终止 / 被中止。被中止的原因：卡片暂停、卡片取消、工作暂停、工作取消、调度者撤销、运行层重启。只有正常完成时才有最终回答，自报结论才有效。
- 调度轮次结束原因同样有"额度用完"和"运行层重启"。
- 卡片状态推导：有派单在跑时跟随该派单（执行中 / 验收中）；没有派单在跑且有前置未满足时为等待前置；前置满足且从未派单为待派单；两次派单之间保持上一次派单对应的状态。已暂停只由用户设置和恢复。
- 工作状态：对齐中只看开头的确认关卡；有未关闭的审核关卡即待审核；退回后回到执行中；"等待用户"不是状态，由未关闭的关卡推导。

### 操作定义与对外接口

- 每个操作只定义一次：名称、参数 schema、哪些调用方能用（用户 / 调度轮次 / 派单）、是否带 `key`。HTTP 路由、MCP 工具和 `helm` 子命令都由它生成，共用同一套实现和约束检查。
- 对外接口只有 HTTP POST + SSE；用户接口不认证。事件接口只有 SSE，不做 Webhook。
- `helm` 命令行是 HTTP 接口的薄客户端，子命令由操作定义生成，覆盖所有用户能用的操作；另有登记项目、设并发上限和 `helm serve`。界面做好后仍保留。
- MCP 端点是 `helmd` 本机 HTTP 上的同一个端点，按令牌区分调用方：调度轮次令牌只能操作所属工作、轮次结束即失效；派单令牌只能用"提交结论"和（需要浏览器时）转发的浏览器工具。
- 违反约束时工具当场返回结构化错误（错误码、一句原因、当前允许做什么），同时记一条"操作被拒绝"事件，不另开轮次通知。
- 新建类操作（建卡片、派单、提关卡、发消息、起草工作说明版本）要求工作内唯一的 `key`，重复时返回已有对象；修改类操作重复执行结果不变。
- 通知接口：列出当前所有待用户处理的事项（待决定的关卡、进入审核的工作、被运行层暂停的工作）；出现新事项时经 SSE 推送"需要用户处理"事件。

### 用户操作

只有这些：发消息、对关卡作决定、打断调度轮次、暂停 / 恢复 / 取消卡片、暂停 / 恢复 / 取消工作、登记项目、设并发上限。每个操作记事件并唤醒调度者；终态、固定关卡不能撤回等约束对用户同样适用。

- 暂停卡片：中止它正在运行的派单，拒绝新派单；恢复后由调度者重新派单。
- 暂停工作：不改卡片状态，中止该工作所有派单，拒绝新派单，暂缓投递自动唤醒；用户消息仍唤醒调度者，用户仍可决定关卡。
- 运行层暂停的工作（调度者额度用完、连续失败 3 次）由用户手动恢复，不做定时唤醒。

### 硬约束（[07](../helm-v1/issues/07-hard-constraints-and-tools.md)）

- 调度者：只能在自己的轮次内操作自己的工作；同一工作同时最多一个轮次；对项目代码只读；不能暂停卡片；不能新建或修改模板。
- 依赖：拒绝成环、跨工作、上游为已取消卡片或已撤回关卡的边；完成、已取消的卡片不能再加依赖；删依赖后前置都满足的下游自动变为待派单；新加依赖不自动撤销正在运行的派单；上游被取消或撤回时下游保持阻塞并唤醒调度者，不自动放行、不连锁取消。
- 派单：卡片等待前置、已暂停、已完成、已取消或已有运行中/排队中的派单时拒绝；工作对齐中、已暂停、已取消时拒绝；执行派单可续跑本卡片以前的执行者对话（须用回原模板和会话 id）或新开，验收派单一律新开；同一会话 id 不能同时被两次派单续跑；并发只计执行者派单（执行和验收都算），全局上限默认 10、可调，满了排队。
- 卡片与关卡：从没正常完成过任何派单的卡片不能标完成，只能取消；需要验收的卡片须最近一次验收派单为通过；完成、已取消是终态；固定关卡不能撤回；审核关卡被接受前工作不能完成。只有用户的决定能关闭关卡。
- 凭据：按模板管住子进程环境变量，清掉会压过订阅的 key；Helm 不读取、不保存、不转发任何 OAuth token。
- 权限代答：`canUseTool` 有 `allow_once` 就选它，只有拒绝项就拒绝并记录，从不选 `allow_always`。

### 驱动接口

- 一个驱动接口，第一版有两个实现：假驱动和 Claude 驱动。调度轮次和派单用同一套驱动。
- 驱动负责：按 cwd、环境变量、沙箱设置、注入的 MCP 服务拉起会话（新开或按会话 id 续跑）；送入内容；取消；把执行者程序的输出逐条交给运行层（带步骤序号）；报告压缩通知；报告结束消息、结束方式（含识别"额度用完"）和 token 用量。
- 结束判定看执行者程序的结束消息（Claude SDK 的 `result`），不看模型文字；进程崩溃看退出码；挂死由看门狗杀进程组。
- 假驱动按脚本回放预先写好的 agent 输出：脚本可以按顺序调用 `helmd` 的 MCP 工具、写副本里的文件、产生步骤输出、以指定结束方式结束、挂住不输出、中途崩溃。它走真实的 MCP 端点和令牌，不绕过约束检查。
- Claude 驱动用 Claude Agent SDK，`pathToClaudeCodeExecutable` 指向本机 `claude`，用户自己登录，Helm 不碰凭证；`settingSources: []`，不读本机全局配置。token 取 result 消息的 `modelUsage`；`compact_boundary` 记一条事件挂在该派单或轮次下。
- Claude 执行者：`permissionMode: 'default'`；`sandbox` 开启、`autoAllowBashIfSandboxed: true`、`allowUnsandboxedCommands: false`、`network.allowLocalBinding: true`；`canUseTool` 拒绝副本以外的 Write/Edit/MultiEdit/NotebookEdit。
- Claude 调度者：cwd 为 `_work`，只读靠 SDK 沙箱不把 `_work` 设为可写；做不到就不给 Bash，只留 Read/Grep/Glob。
- MCP 注入：`mcpServers` 用 `type: 'http'` 带 `Authorization` 头。动态 HTTP MCP 出现 `needs-auth` 时改用每轮/每派单一个 stdio 转发小程序（带令牌连 HTTP），令牌和作用范围不变。本机有代理环境变量时设 `NO_PROXY` 含 `127.0.0.1,localhost`。

### 执行派单

- 卡片副本：卡片第一次派单时从工作分支当前末端开出 worktree，放在 `~/.helm/worktrees/<工作>/<卡片>`，分支 `helm-card/<工作>/<卡片>`；同一卡片的后续派单都复用。
- 派单开始前检查副本 `git status`（被 ignore 的文件不算），不干净就记事件列出被改文件，重置到卡片分支 HEAD 再派单。
- 每次派单分配一段本机端口，用环境变量传给执行者。
- 执行者环境里用 `GIT_CONFIG_*` 设置 `url.<无效地址>.pushInsteadOf` 覆盖 `git@`、`https://`、`ssh://`，并给一个无效的 `GH_TOKEN`。
- 看门狗：墙钟总时长和无输出时长两个阈值，可调；超时杀进程组，结束方式记为超时终止。
- 任何结束方式之后，先对工作目录在该副本里的进程连同进程组发 `SIGTERM`，5 秒后仍存活的发 `SIGKILL`（按工作目录查找进程），再处理 git。
- 执行派单结束后：删残留的 `index.lock`，abort 进行中的 merge、rebase、cherry-pick、revert（记事件），把剩余改动提交一次，提交信息写派单 id 和结束方式。执行者自己提交不禁止。

### 验收与浏览器（[09](../helm-v1/issues/09-acceptance.md)）

- 每次派单都注入"提交结论"工具：执行派单可选完成 / 受阻，验收派单可选通过 / 不通过，另附一句理由；可多次调用，以结束时最后一次为准；调用不结束派单；没调用记为未声明。未声明不算通过，调度者不能改判。
- 验收派单：内容前由运行层附上派单时的卡片说明快照，并记下生效的工作说明版本；开始时记卡片分支 HEAD，结束后（先清进程）`git reset --hard <该 HEAD>` 加 `git clean -fd`，保留被 ignore 的依赖和缓存。
- 整体验收卡片是普通卡片：需要验收、依赖所有其他卡片、只派验收派单；标完成时没有新提交，合并跳过。
- 派单标了"需要浏览器"时，`helmd` 在沙箱外为这次派单起一个 Playwright MCP（`@playwright/mcp`，HTTP 模式，`--isolated`，Playwright 自带 Chromium、有界面，锁定版本并按版本装浏览器，用 127.0.0.1 时加 `--allowed-hosts`），派单结束即关。`helmd` 通过派单 MCP 端点只转发检查所需的浏览器工具（navigate、snapshot、click、type、screenshot 等），不暴露 `browser_evaluate`、`browser_run_code_unsafe`。Playwright MCP 进程组记 pgid 和启动时间。

### 合并

- 调度者标记完成时，`helmd` 在同一个操作里先在 `_work` 把卡片分支 `--no-ff` 合进工作分支，成功才写"完成"；冲突时中止合并、卡片状态不变，返回"与工作分支冲突"。修复卡片从工作分支末端开出，把冲突卡片的分支合进来解决冲突；它完成后再标冲突卡片完成，合并为"已是最新"，直接成功。
- 卡片进入终态时删除它的 worktree 和卡片分支；工作结束（审核接受或取消）时删除 `_work`；工作分支保留。
- 审核接受后：`git merge-tree --write-tree <基准分支> helm/<工作>` 预检；有冲突就不合并，在对话里报告冲突文件和工作分支名。无冲突时，基准分支未在用户项目目录检出就用 `commit-tree` + `update-ref` 直接写分支；已检出就在项目目录里 `git merge --no-ff`，git 拒绝时只报告。然后推送基准分支。不论成败工作都进入已完成，结果记成事件。

### 调度轮次（[06](../helm-v1/issues/06-coordinator-lifecycle.md)）

- 唤醒事件：卡片变为待派单、派单结束、用户发来消息、关卡有了决定（含审核退回）、上游被取消或撤回导致下游卡住、用户的直接操作。事件进入该工作的队列；没有轮次在跑时合成一轮投递，每条只写"什么事 + 指向哪张卡片或哪次派单"。
- 每轮新开一个 CLI 会话，不续跑上一轮；运行层每轮拼启动简报：① 工作说明（对齐阶段为草稿并标"未确认"）；② 卡片图摘要，每卡一行（状态、依赖、执行者、最近一次派单的结束方式和自报结论）；③ 未决关卡；④ 调度笔记全文；⑤ 上一轮以来的新事件；⑥ 最近 20 条对话（不含执行者输出）。
- 轮次正常结束后才把投递的事件标为已处理。失败（崩溃、出错退出、超时、上下文溢出）就开新一轮重投，附"上一轮中断，期间已做的操作见任务库"；连续失败 3 次暂停工作并在对话里发运行层消息。额度用完直接暂停工作，不重投。运行层重启导致的结束不计失败。
- 看门狗：每轮总时长默认 30 分钟、无输出 10 分钟，可调。轮次结束后同样清理 `_work` 里的残留进程。
- 打断：取消当前轮次，立即开新一轮，被取消轮次的事件连同用户消息一起重投，不算失败。
- 工作审核接受或取消后不再唤醒；工作暂停期间只投用户消息。

### 默认调度者提示词

第一版只放简短提示词，要能跑通完整流程，至少写明：整项工作要有整体验收卡片；验收通过后不再给这张卡片派执行单，改动走新卡片；标完成冲突时建修复卡片；优先用不同模板交叉验收，只有一家时同家也可；验收卡片的说明写清本卡相关的边界和标准，整体验收卡片写工作说明的标准；执行者额度用完时改派，无处可派就提关卡；决策关卡尽量少提，参考情形为中途修改冲突太大、需要密钥或凭据、超出边界或需改工作说明、多次返工仍失败或多个执行者受阻、标准判断不了的取舍；汇总报告逐卡写结果、验收是否通过、由谁完成并附成果链接；调度笔记控制在约 4k token；不推送、不部署。执行者提示词写明不推送、不部署，开发服务用分配的端口，检查过程和证据写进最终回答，最后调用"提交结论"。

### 启动对账（[11](../helm-v1/issues/11-persistence-and-recovery.md)）

按顺序：先杀进程，再动 git。

1. 工作目录在 `~/.helm/worktrees/` 下的进程连同进程组，先 `SIGTERM` 后 `SIGKILL`；库里记的 Playwright MCP 进程组仍存活且启动时间对得上的杀整组、回收端口段。
2. 运行中的派单记"被中止：运行层重启"并唤醒调度者；运行中的执行派单补提交。运行中的调度轮次记结束（运行层重启），事件重投。
3. `_work` 半截合并 `merge --abort`；用户项目目录留有 helmd 发起、指向工作分支的 `MERGE_HEAD` 时先 abort；已完成但缺合并或推送结果事件的工作补做（基准分支已包含工作分支就跳过合并）。
4. 补删终态卡片残留的 worktree 和卡片分支、已结束工作残留的 `_work`。

排队中的派单保持排队，未处理的唤醒事件照常投递，已暂停的工作保持暂停。正常停止与崩溃走同一路径。

## Testing Decisions

- **好测试**只经外部接口断言外部行为：HTTP 读到的状态、SSE 收到的事件、MCP 工具的返回、git 仓库和文件系统的实际状态。不读表、不测内部函数。
- **主边界**：测试里起一个真的 `helmd`（临时数据目录、临时 git 仓库），驱动换成假驱动。用户一侧走 HTTP + SSE（`helm` 命令行由操作定义生成，不单独逐条测）；调度者和执行者一侧由假驱动脚本经真实 MCP 端点调用工具。至少覆盖：
  - 对齐与确认关卡、工作说明版本、工作分支开出
  - 依赖约束（成环、跨工作、上游取消或撤回后下游卡住并唤醒）、关卡阻塞
  - 派单约束、并发上限与排队、看门狗超时、端口段分配
  - `key` 去重：同一批事件重投不重复建卡和派单
  - 卡片状态推导、标完成条件（含整体验收卡片）、"提交结论"取值与未声明
  - 执行派单任何结束都提交（含残留 `index.lock`、合并到一半）、验收派单结束后重置、派单开始前副本不干净时重置、残留进程被清理
  - 标完成合并、冲突被拒、修复卡片后再标完成成功
  - 审核接受：预检冲突只报告、基准分支检出与未检出两条合并路径（推送用本地 bare 仓库作远端）、退回后重新审核
  - 调度轮次：事件合并投递、同一工作最多一个轮次、打断、失败重投、连续失败 3 次暂停、额度用完暂停、令牌只能操作所属工作且轮次结束失效
  - 暂停、恢复、取消卡片和工作
  - 启动对账：在各个中间状态杀掉 `helmd` 再启动
  - 通知接口和"需要用户处理"事件、违规返回结构化错误并记"操作被拒绝"事件
- **副边界**：驱动接口，只用于 Claude 驱动的冒烟测试，用真 CLI、消耗小的模型、低推理强度。验收项为原 14 的技术验证：① Claude SDK 能按会话加载带令牌的 HTTP MCP，调度者能用它建卡、派单、改依赖，"提交结论"和转发的浏览器工具在同一端点工作；② 重投时靠 `key` 不重复；③ Claude 调度者在 `_work` 里用 Bash 写文件被拦，Claude 执行者副本外的 Write 被 `canUseTool` 拒绝；⑤ 动态 HTTP MCP 的 `needs-auth` 多跑几轮看是否复现，复现就切到 stdio 转发。另测 token 记录和结束方式识别。
- **浏览器**：起真实浏览器的测试（Playwright MCP、浏览器验收）不在沙箱里跑，用 Playwright 自带的 Chrome for Testing 有界面模式，与其余自动测试分开运行，验收时要看截图。
- **端到端验收**（不是测试边界）：网页版 2048，期望拆成 4～5 张有依赖的卡片（游戏逻辑、渲染、计分和存档、重开按钮等），含浏览器验收，用真实 Claude 驱动跑一次完整流程。合并冲突不强求，出现了就顺带检查修复卡片。
- **先例**：仓库还没有产品代码和测试。可参考未提交的实测脚本（驱动探针、沙箱、MCP 转发、恢复实测，在 `.scratch/prototype/` 下），它们记录了各项设置的实测用法，不作为测试复用。

## Out of Scope

- **第二阶段**：Codex 驱动（含原 14 技术验证④⑥、token 记录、额度用完）、用户级服务自启动（`helm service install`）、输出管理（工作结束后 gzip、10 GB 提示、导出和删除输出）、换调度者模板、新增或修改 Agent 模板。模板配置：调度者、执行者各一份，包括提示词（即策略）、skill、工具调整，放在 Helm 仓库里的配置目录，每个调度轮次、每次派单开始时读取，改了不用改代码或重启；Helm 自己的 MCP 工具、沙箱、凭据过滤和运行层约定（端口、提交结论、进程清理、截图路径、不推送）留在代码里，不进配置。会话记录隔离：Helm 拉起的所有 agent CLI（Claude Code、Codex，以及第三阶段的 Grok、DeepSeek）用 Helm 专用主目录 `~/.helm/agent-homes/<cli>/`（`CLAUDE_CONFIG_DIR`、`CODEX_HOME`、`GROK_HOME`、`DSH_HOME`），会话记录和配置与用户在 Helm 之外的使用分开。登录：Codex、Grok、dsh 由 Helm 在专用目录建软链接指向用户原来的凭据文件，沿用用户的登录；Claude 的登录在钥匙串里、按配置目录区分，用户在专用目录 `claude auth login` 一次。Helm 只建链接，不打开、不复制、不转发凭据。实测见 [第二阶段待办](../helm-v1-p2/issues/01-agent-home-isolation.md)。
- **第三阶段**：界面（前置条件是用户的前端设计）、Grok 和 DeepSeek 的 ACP 驱动、界面做完后再跑一次 2048。Grok 驱动关掉 `~/.claude/`、`~/.cursor/` 规则来源，与 Claude 驱动 `settingSources: []` 一样不读本机全局配置；关法届时实测，来由见 [第二阶段待办 01](../helm-v1-p2/issues/01-agent-home-isolation.md)。
- 调度者能力（A1、A2）的验证，以及对齐确认、关卡判断、汇总报告、拆单派单返工等调度者技能：用户在 Helm 之外另做。
- 执行者外层隔离（Seatbelt 外壳、独立系统用户、容器、VM）。
- 用户接口认证、跨站请求和 DNS 重绑定防护：v1 已接受的风险。
- 系统通知、推送到手机；账户剩余额度百分比、美元花费统计。
- 回放播放器、逐行批注、部分接受审核。
- 软件项目以外的工作类型、关机后继续运行、远程访问。
- 项目初始化命令、密钥复制：执行者自己装依赖，需要密钥时调度者提关卡。

## Further Notes

- 所有实测都在 macOS 上做；v1 目标是 macOS 和 Linux，Linux 上的沙箱、按工作目录找进程、`merge-tree` 版本要求还没实测。
- 执行者额度用完在冒烟测试里很难真正触发，怎么验证 Claude 驱动的识别还没定。
- 已接受的风险：执行者能在沙箱里连到 `helmd` 冒充用户；可写范围超出副本的部分（各家状态目录、`/tmp`）；用 `setsid` 或先 `cd` 出副本的进程清不到；用户在副本目录里开的终端会被杀（文档要提示看代码去工作分支）；浏览器在沙箱外写 Chrome for Testing 的 Crashpad 目录。
- 开发测试用真实驱动时一律用消耗小的模型、调低推理强度。
- 开发任务单在 [issues/](issues/)，共 15 张，按各单的 Blocked by 推进。
