# 任务 001：原型 v2——吸收长任务纪律的 7 项改进

## 背景

Helm 是一个"契约驱动"的 ADE：任何工作都拆成 需求 + 边界 + 开发 + 测试。人只定义、理解、签收 需求 / 边界 / 测试；开发由代理完成。代理角色：chief（拆解派单）、worker（执行）、verifier（核对证据）、redteam（挑错）。

`prototype/index.html` 是一个纯前端、可点击的产品原型（模拟数据，无后端），供产品负责人审核交互与概念。本任务在其基础上新增 7 项能力。

**先读这些文件：**
- `DESIGN.md`：整体设计
- `prototype/index.html`：现有原型（单文件，内联 CSS + JS，所有模拟数据在 `const db = {...}` 中）

## 要做的内容

所有改动只在 `prototype/index.html` 中完成。保持单文件、零外部依赖、无构建步骤。界面文字使用中文。

### 1. 边界区分「强制」与「建议」

- 每条边界增加字段 `enf`：`'enforced'` 或 `'advisory'`；强制边界再带 `mech`（保证机制的说明文字）。
- 强制边界前显示 🔒 和"强制"标签，并在来源行展示机制；建议边界显示"建议 · verifier 核对"。
- 在收件箱顶部说明区的图例中，加入这两种边界的说明。
- 为现有模拟数据补齐字段，要求合理，例如：
  - c1「不直接联系客户」→ 强制，机制："worker 未被授予邮件 / IM 类工具"
  - c2「复用调度引擎 v3，不修改 engine/ 目录」→ 强制，机制："Claude Code 权限规则 deny Edit(engine/**) + 确定性测试 t2"
  - c2「不新增第三方依赖」→ 强制，机制："确定性测试 t2"
  - c1c「毛利率不低于 35%」（来自变更请求）→ 建议
  - 其余边界按语义自行判断。
- 草稿状态下"补充一条边界"的输入行旁边，增加一个下拉框，用于选择强制或建议，默认为建议。

### 2. 契约新增「交付物 / 资料来源 / 上限」

- 每个契约增加：
  - `deliverable`：交付物，包括形式和路径
  - `sources`：允许使用的资料来源，字符串数组
  - `limit`：上限，包括截止时间、最大尝试次数、预算 token 数，以及当前已用的尝试次数和 token
- 在契约详情页，标题区下方、三栏之上，新增一条信息带，展示交付物、资料来源和上限。
- 上限展示进度条：尝试次数和 token 各一条。已用超过 80% 时显示警告色，达到 100% 时显示错误色。
- 为所有契约补齐合理的模拟数据。草稿契约的已用量为 0。

### 3. 新增「达到上限」阻塞场景

- 在 c1 下新增第 4 个子契约 `c1d`「竞品与市场规模调研」，状态为 `blocked`，阻塞原因是达到上限（token 已用 100%）。
- 阻塞横幅需要区分两种类型：
  - **提问型**：现有的 c1b，保持不变
  - **达到上限型**：显示"已达上限"和一份部分完成报告，内容包括已完成、未完成、继续完成预计还需多少，并提供三个按钮：
    - 「追加预算」：token 上限 +50%，状态回到 running，写入日志
    - 「调整契约」：在需求中追加一段文字。用 `prompt()` 输入，状态回到 running，契约版本 +1
    - 「终止」：新增状态 `abandoned`（中文为「已终止」，灰色），写入日志
- `c1d` 必须出现在收件箱的"阻塞"分组中，并注明阻塞类型。

### 4. 交接记录（Handoff）卡片

- 每个已开工的契约（状态不是 draft）增加 `handoff`，字段包括：`updated`（时间与更新者）、`baseline`（基线）、`done`（已完成，数组）、`decisions`（决策及依据，数组）、`open`（未解决问题，数组）、`next`（下一步动作，单条）、`outputs`（产出路径，数组）。
- 在详情页下方区域新增一张"交接记录"卡片，排在开发过程卡片之前。卡片上注明："新会话认领时先读这里，并核对引用的文件"。
- 基线示例：
  - c1a："引擎 v3 官方规格支持 ≤ 200 台设备；已知无双向同步交付记录"
  - c1d："已有 2025 年行业报告 1 份（可能过期）"

### 5. 执行记录（Attempts）

- 契约增加 `attempts` 数组，每一条包含：序号、执行者（agent:worker 等）、模型与 effort（例如 "opus-5.5 · high"）、方法、结果（成功 / 失败 / 进行中 / 达到上限）、失败原因、token 用量、耗时。
- 把"开发过程"卡片改为两个页签：「执行记录」（默认）和「时间线」，时间线即现有日志。整张卡片仍然默认折叠。
- 失败的尝试要醒目展示失败原因，并标注"后续尝试不得重复此方法，除非有新理由"。
- 模拟数据：
  - c1a：#1 失败（redteam：基准未覆盖插单场景），#2 成功
  - c1c：#1 进行中
  - c1d：#1 达到上限
  - c1b：#1 进行中，处于阻塞状态

### 6. 检查结果增加「无法判定」，并记录方法与修正

- 测试结果新增 `unresolved`，中文为「? 无法判定」，使用警告色。
- 证据下的每条检查记录增加：
  - `method`："独立代理复核" 或 "同上下文复核"
  - `correction`：不通过之后修正了什么，可以为空
- 修改模拟数据：c1a 的测试 t2（ERP 对接方式）中，"无双向实时同步的交付记录"这条证据，由 verifier 判为 `unresolved`，说明为"检索为空只能证明经验库无记录，不能证明公司从未做过，需人确认"。t2 整体结果因此是 unresolved。
- 规则：契约处于 `in_review` 时，如果还有 unresolved 的测试：
  - 测试行旁边显示「判为通过」和「判为不通过」两个按钮，只有人可以点。点击后记录一条 `checker: human` 的检查，方法为"人工判定"。
  - 在全部 unresolved 被判定之前，「签收」按钮禁用，并显示提示文字。「打回」不受影响。
- c1a 现有的 redteam 检查链（先不通过、后通过）补上 correction："补充 P-2024-07 插单率 18% 场景数据"。

### 7. 签收后沉淀为模板

- 侧栏新增「模板」分区，初始为空，显示"签收后可沉淀为模板"。
- 任何契约签收（accepted）后，在其详情页的"已签收"横幅中提供「保存为模板」按钮：
  - 点击后用 `prompt()` 输入模板名，默认值为契约标题
  - 生成的模板包含：需求（作为说明）、边界（保留强制 / 建议标记）、测试（保留类型）、子契约标题列表
  - 模板出现在侧栏，点击后打开只读的模板详情页，用同样的三栏布局，并在顶部说明："chief 下次起草同类契约时会以此为起点，你需要确认的内容会更少"
  - 同一个契约只能保存一次。保存后按钮变为"已保存为模板「xxx」"。

### 8. worker 启动 prompt 预览

- 在契约详情页的标题区操作按钮中，增加一个次要按钮「worker 启动 prompt」，所有状态下都可以点击。
- 点击后弹出模态框（自行实现，不用 `alert`），展示由当前契约字段自动生成的启动 prompt。结构如下：

```
<goal>完成 {需求}。在 {交付物} 留下可用结果、验证证据和交接记录。达到全部测试或上限即停止。</goal>
<inputs>
Task: {需求}
Output: {交付物}
Checks: {测试列表，带类型}
Sources: {资料来源}
Scope: {边界列表，强制边界标 [强制]}
Limit: {截止 / 尝试次数 / token}
</inputs>
<rules>
- 先读 handoff，再核对其引用的文件，不要直接相信记录的状态
- 第一步记录基线
- 不得放宽测试来换取通过；契约问题只能通过 propose_change 提出
- 不得重复已失败的方法，除非有新理由（附上失败记录摘要）
- 每完成一个阶段调用 save_handoff
- 证据通过 submit_evidence 提交；验证由 verifier 完成，你不自评
</rules>
```

  其中 handoff 和失败记录摘要取自该契约的实际数据。
- 模态框需要提供"复制"按钮（使用 `navigator.clipboard`，失败时提示"复制失败"）和关闭按钮，并且支持 Esc 关闭。

## 不要做的内容（边界）

- 不得修改 `prototype/` 以外的任何文件，例外是：本任务的报告文件、`evidence/001/` 下的证据文件。尤其不要改 `DESIGN.md`、`src/`、`package.json`、`.claude/`。
- 不引入任何外部库、CDN、字体或构建工具。
- 不删除或改变现有功能：收件箱 4 个分组、批准契约（含边界勾选）、回答阻塞、审批变更请求、签收 / 打回、契约树、深色模式、窄屏布局（≤ 760px 单列）。
- 不要重写整体视觉风格。新元素沿用现有的 CSS 变量和组件样式（chip、card、banner 等）。新颜色必须定义为 `:root` 变量，并在深色模式块中同步定义。
- 保持现有所有模拟数据的内容和语义不变，只做本任务要求的增补和修改。
- 本任务是实现任务，不要做浏览器检查。浏览器检查会单独安排。

## 必须有的测试

在 `evidence/001/check.mjs` 写一个 Node 脚本，不依赖第三方包，只用 Node 内置模块。脚本要求：

1. 从 `prototype/index.html` 中提取 `<script>` 内容。
2. 用最小的 DOM 桩（stub）执行脚本：`document.querySelector` 返回一个可以写入 `innerHTML` 的对象即可；`prompt`、`navigator.clipboard` 也用桩替代。然后通过暴露的全局函数驱动状态，并断言：
   - T1：c1d 存在，状态为 blocked，并出现在收件箱的阻塞列表中
   - T2：对 c1d「追加预算」后，token 上限变为原来的 1.5 倍，状态为 running
   - T3：c1a 初始时存在 unresolved 测试，此时调用签收应被拒绝，状态仍是 in_review；把 unresolved 判为通过后，签收成功，状态为 accepted
   - T4：c1a 签收后保存为模板，模板列表 +1；再次保存不会重复增加
   - T5：生成的 worker 启动 prompt 中，包含 c1a 的需求文本、至少一条 `[强制]` 边界（任选一个含强制边界的契约），以及失败尝试的摘要
   - T6：既有流程回归：批准 c2（先确认全部边界）后，c2 及其子契约离开 draft；批准 c1c 的变更请求后，版本 +1，并且新增的边界是"建议"类型
   - T7：所有契约都有 deliverable、sources、limit 字段；所有非 draft 契约都有 handoff 和 attempts
3. 每条断言输出 `PASS/FAIL Tn 描述`，全部通过时退出码为 0。

为了便于测试，可以把需要的函数挂在 `window` 或全局上，但不要为测试而改变界面行为。

## 验证命令与验收标准

1. 基线：在改动之前，先运行一次提取脚本并执行 `node --check`，确认原脚本语法正确，把结果记入报告。
2. `node evidence/001/check.mjs` 全部通过，完整输出保存到 `evidence/001/check-output.txt`。
3. 把提取出的脚本保存为临时文件并执行 `node --check`，语法检查通过，结果写入报告。
4. `git diff --stat` 只包含 `prototype/index.html` 和 `evidence/001/`，以及报告文件。
5. 清理自己创建的临时文件，证据文件除外。
