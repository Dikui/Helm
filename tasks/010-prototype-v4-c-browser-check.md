# 任务 010：原型补漏浏览器页面检查（只检查，不改代码）

## 背景

任务 009 在 `prototype/index.html` 中补充了产出物预览抽屉、合并队列与冲突（示例项目 C）、预置阻塞型发现（见 `tasks/009-prototype-v4-c.md`、`evidence/009/report.md`）。本任务在真实浏览器中检查这些内容，并回归任务 008 的检查。

## 要做的内容

1. 启动静态服务：`python3 -m http.server <空闲端口> -d prototype`，端口自选，不要用 8787。无头浏览器（Playwright 安装在项目目录以外，或本机 Chrome headless），视口 1440×900，浅色模式。
2. 场景（每个至少一张整页截图，保存到 `evidence/010/`，文件名以场景编号开头）：
   - S01 收件箱：恰好 11 个分组，「合并冲突」分组有条目
   - S02 项目 B「浏览器检查」：从第 1 次尝试的一条失败条目打开来源，抽屉显示真实 `evidence/002/assertions.txt` 内容并高亮对应行；从第 2 次尝试的一条条目打开，显示 `evidence/002/recheck-1/assertions.txt` 并高亮。用脚本读取真实文件，断言高亮行文字与文件对应行逐字一致
   - S03 项目 A：打开一个 Markdown 交付物（标题、列表、代码块渲染正确）和一个 CSV 资料（表格），两者标注"示例"
   - S04 打开 `--ok` 颜色变更的 diff：带行号，新增 / 删除行同时有 `+` / `-` 符号与颜色，显示来源提交号
   - S05 抽屉交互：关闭按钮与 Esc 均能关闭，关闭后焦点回到触发元素
   - S06 项目 C 项目页：合并队列按验收先后排列，后合并者标"需 rebase"，有冲突项；所有数据标注"示例"
   - S07 合并冲突：查看 leader 的尝试记录；从收件箱选择"已手动解决，继续合并"，决策记录中出现该决策（截前后）
   - S08 项目 A 显示"验收后发布"且无合并队列；项目 B 显示合并信息未记录的说明及项目 C 入口
   - S09 阻塞型发现：从收件箱批准"起草新节点"，原节点显示暂停并依赖新节点；用页面上的模拟操作让新节点提交并验收，原节点恢复（截三张：批准前、暂停中、恢复后）
   - S10 术语扫描：所有页面（含项目 C 及其节点、抽屉外框）可见文本不出现"契约""chief""worker""签收""Hub"；嵌入的真实 assertions 原文除外（说明如何排除），列出扫描页面数
   - S11 深色模式：收件箱、项目 C 合并队列、打开 diff 的抽屉
   - S12 窄屏 375×812：收件箱、项目 C 项目页、打开真实证据的抽屉；断言无横向滚动、抽屉占满宽度、正文列宽 ≥ 280px、文字没有被挤成逐字换行
3. **回归任务 008**：复制 `evidence/008/browser-check.mjs` 到 `evidence/010/regression-008/` 下运行（不改原脚本和原证据），预期因收件箱由 10 组变为 11 组而有个别断言失败；对每条失败判断是预期变更还是回归问题。
4. 控制台 error、warning、未捕获异常保存到 `evidence/010/console.txt`，没有写"无"。
5. 每个场景用 DOM 查询或页面文本断言，结果保存到 `evidence/010/assertions.txt`，每行 `PASS/FAIL Sxx 描述`。S11、S12 中用 `getComputedStyle` 抽查抽屉文字、diff 增删行、高亮行、合并状态标签、链接的对比度 ≥ 4.5:1。
6. 检查脚本保存为 `evidence/010/browser-check.mjs`。
