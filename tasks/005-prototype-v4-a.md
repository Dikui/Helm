# 任务 005：原型更新 A——结构与术语迁移到 v3 模型

## 背景

`prototype/index.html` 是 Helm 的单文件可点击原型（纯前端、模拟数据、无后端）。它目前停在 v2（"契约树"阶段）：使用"契约"、chief / worker / verifier / redteam、签收等旧术语，结构是契约树。产品规格已经更新到 v4（`FEATURES.md`）。

原型更新分三步：**本任务 A** 把原型迁移到 v4 规格中的基础模型（即 v3 已有的部分）；任务 B 再加入 v4 新增内容；每步之后各有一次单独的浏览器检查。**本任务不做 v4 新增内容，也不做浏览器检查。**

**先读这些文件：**
- `FEATURES.md`：产品规格 v4。本任务对应其中 §0（术语）、§1.1–1.3、§1.8–1.9、§1.12–1.13、§1.15、§2 的 B1–B10、§3、§4、§6、§7
- `prototype/index.html`：现有原型（单文件，内联 CSS + JS，模拟数据在 `const db = {...}`）
- `tasks/001-prototype-v2.md`、`tasks/001-report.md`：v2 已有的能力，本任务必须保留
- `tasks/001-rework-1.md`、`tasks/002-*.md`、`evidence/001/`、`evidence/002/`：项目 B 真实数据的来源

## 要做的内容

所有改动只在 `prototype/index.html` 中完成。保持单文件、零外部依赖、无构建步骤。界面文字使用中文。

### 1. 术语迁移（只针对界面上显示的文字）

| 旧 | 新 |
|---|---|
| 契约 | 项目（顶层）/ 节点（项目流程中的一项） |
| 契约树 | 项目流程 |
| chief | leader |
| worker / verifier / redteam | 席位：执行 / 核对 / 挑错（显示坐在该席位上的代理名） |
| 签收 / 待签收 / 已签收 | 验收 / 待验收 / 已验收 |
| worker 启动 prompt | 执行代理启动 prompt |
| Hub | runtime |

- 代码内部的变量名、函数名可以保留旧名，也可以改名，自行决定；但**渲染到页面上的文字**不得再出现"契约""chief""worker""签收""Hub"。
- 执行端显示为 Codex CLI；Claude Code、Gemini CLI 显示为「即将支持」（FEATURES §5）。

### 2. 数据模型：项目 → 项目流程 → 节点

- 顶层是**项目列表**。每个项目有：名称、类型（产品开发 / 客户交付 / 调研 / 空白）、工作现场（git 仓库或文档目录，显示路径即可）、leader（代理库中的一个代理）、项目流程、执行者配置、自主度设置。
- **项目流程**：节点 + 依赖边，支持顺序、并行、条件分支（分支边上带条件文字，如"若可行"）。不支持嵌套。
- **节点**保留 v2 契约的全部字段（需求、边界含强制 / 建议与机制、测试含四类与检查记录、交付物、资料来源、上限、交接记录、执行记录、日志等），并增加：
  - 席位安排：执行席位（代理 ID，或标为人工节点）、核对席位、挑错席位（仅当含对抗型测试时）
  - 上下文包（见第 6 项）
  - 依赖的前置节点
- 节点之间按依赖控制启动：所有前置节点已验收，节点才能启动。

### 3. Demo 数据：替换为 FEATURES §7 的两个项目

- **项目 A：客户 A · 智能排产承接**（客户交付）
  项目流程：需求澄清 → [技术可行性 ∥ 交付产能 ∥ 成本报价 ∥ 市场调研] → 汇总结论 →（可行）起草交付项目 /（不可行）婉拒说明
  - 尽量复用 v2 中客户 A 相关契约的内容（技术可行性、交付产能的提问、成本报价的变更请求、市场调研的达到上限等），映射到对应节点，保证 v2 的典型场景都还在：一个待验收且含"无法判定"测试的节点、一个提问阻塞的节点、一个达到上限的节点、一个含变更请求的节点、一个草稿待批准的节点。
- **项目 B：Helm 原型 v2 开发**（产品开发，**使用真实开发记录**）
  项目流程：功能规格 → 实现（Codex）→ 浏览器检查 → 你审核
  - 数据从 `tasks/001*`、`tasks/002*` 和 `evidence/001/`、`evidence/002/` 中取真实内容：浏览器检查第 1 次 31/34，**退回到「实现」节点**（窄屏挤压、对比度不足）→ 实现第 2 次尝试 → 浏览器检查第 2 次 38/38；变更请求（`--ok` 颜色 #1f8a4c → #1f874c）；测试本身写错的例子（S03 断言 → 通过项目变更修正，不走退回）。
  - 真实的 Codex 会话 ID：如果在仓库文件中找得到就使用；找不到就显示"未记录"，**不得编造**，并在报告中列出。
  - 凡是从仓库记录中取的数字和文字，在报告中注明来源文件。

### 4. 页面

- **收件箱**（首页）：只列需要人处理的事，分为 6 组：待批准、提问、达到上限、变更请求与退回请求、待验收、待审核的经验库条目。每项点击进入对应节点。
- **项目页**：项目流程图，节点按状态着色，点击节点打开节点详情；并行与条件分支要能看出来（条件写在边旁）。用内联 SVG 或 CSS 布局自行实现，不引入库。
- **节点详情**：信息带（交付物、资料来源、上限进度）、需求 / 边界 / 测试三栏、席位、上下文包、验收报告、交接记录、开发过程（执行记录 / 时间线，默认折叠）。
- **代理库**：代理列表（含表现统计）、设计代理表单、待批准的代理提议与教训建议（FEATURES §1.15）。
- **经验库**：保留并沿用 v2 的内容，显示条目被哪些项目引用、待审核条目。
- **决策记录**：采纳率统计、决策列表、自主度设置（FEATURES §4 中 v3 已有的决策点：批准节点项目、审批变更请求、退回请求、处理达到上限、判定「无法判定」、验收、上下文包确认；以及始终由人的经验库入库、不可逆或对外动作）。
- **项目设置**：执行者配置、自主度设置入口、工作现场。
- 侧栏：收件箱、项目列表（展开可见项目流程中的节点）、知识（经验库、决策记录、代理库）、模板。

### 5. 行为

- **两次确认**（FEATURES §1.2）：开工时批准节点项目（保留 v2 的逐条确认边界）；节点就绪前（上游全部验收后）leader 根据上游产出补全细节，有变化则进入收件箱"待批准"并显示差异，无变化则直接开工。至少用一个节点演示"有变化"。
- **提问**：leader 先回答；能回答的写入决策记录、不进收件箱；回答不了的进入收件箱"提问"。至少各有一例。
- **退回**（FEATURES §1.9）：下游节点提出"退回到某个节点"，附理由和证据；默认由人批准。批准后：被退回节点重新打开，理由写入它的交接记录；受影响的下游节点作废（标为需重新验证）；不受影响的节点保留结果。同一节点最多被退回 2 次（常量可配置），第 3 次请求转为"升级给你处理"。
- **变更请求**：保留 v2 行为；编辑已批准的节点项目时版本 +1；测试写错走项目变更而不是退回。
- **验收**：保留 v2 规则（存在无法判定的测试时不能验收）。leader 不能验收、不能修改项目——如果用 leader 身份调用验收或修改，必须被拒绝。
- **达到上限**：保留 v2 的追加预算 / 调整 / 终止。
- **代理库**：人可以直接创建代理（表单字段见 FEATURES §1.15，至少：名称、擅长的任务、模型与强度、可以担任的席位）；leader 提议的新代理需人批准后才进入列表。内置 4 个模板：通用执行、通用核对、通用挑错、通用项目经理（默认模型见 FEATURES §5，本任务只需"作为主 agent"一列）。
- **席位**：坐核对或挑错席位的代理，在节点上标注"只读 · 新上下文"；一个节点只有一个执行代理。
- **自主度**：每个决策点可切换「由我决定 / 代理自动」，按项目类型保存。至少实现"批准节点项目"设为自动后的效果：leader 起草后直接开工，决策记录标注决策者。
- **决策记录**：所有决策写入，标注决策者（你 / leader / 自动）以及"原样采纳 / 有修改 / 驳回"，显示采纳率。
- **模板**：保留 v2 的"验收后保存为模板"，模板对应项目类型。
- **执行代理启动 prompt**：保留 v2 的模态框和结构，把其中的术语按第 1 项替换；工具名可改为与 v4 一致的描述，结构不变。

### 6. 上下文包（FEATURES §1.13）

- 每个已开工的节点有一份上下文包：列出**发送了哪些信息、不发送哪些信息，以及原因**。
- 至少包含一个"不发送"的例子，原因是"与本节点无关"（如商务信息不发给写代码的节点）；以及一个原因是"保持复核独立"（如检查思路不发给执行者）。
- 在节点详情中可查看；自主度中"上下文包确认"默认为自动。

## 验证命令与验收标准

1. **基线**：改动前运行 `node evidence/001/check.mjs`，并对提取的脚本执行 `node --check`，结果保存到 `evidence/005/baseline.txt`。改动后 `evidence/001/check.mjs` 预计会因数据模型变更而失败——这是已知、预期的，不需要修复它；在报告中说明哪些旧断言由新测试的哪一条覆盖。
2. `node evidence/005/check.mjs` 全部通过，完整输出保存到 `evidence/005/check-output.txt`。
3. 提取改动后的脚本执行 `node --check` 通过，结果写入 `evidence/005/syntax-check.txt`。
4. 新增颜色的对比度：沿用 `evidence/001/contrast-check.mjs` 的方法，检查新增前景 / 背景组合在浅色与深色模式下的对比度 ≥ 4.5:1，结果保存到 `evidence/005/contrast-check.txt`。
5. `git status` 只新增或修改：`prototype/index.html`、`evidence/005/`、本任务报告文件（以及已存在的未跟踪任务说明文件）。
6. 清理自己创建的临时文件；证据文件保留。
