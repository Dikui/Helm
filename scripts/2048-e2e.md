# 2048 真实 Claude 与浏览器运行步骤

这是任务单 15 的第二段，在沙箱外、有显示服务的 macOS/Linux 机器上执行。会消耗本机 Claude 订阅额度并启动有界面的 Chrome for Testing。不要在 Codex 沙箱内运行 `serve` / `start`。本脚本不在 `npm test` 中。

准备 Node >=22.13、支持 `merge-tree --write-tree` 的 git、本机已登录的 `claude`（`claude --version` 可用），以及 Claude SDK 所需的本机沙箱依赖（Linux 需 bubblewrap、socat，macOS 需 lsof）。保持 Claude 的登录环境，勿把 `HOME` 改到临时目录。浏览器使用锁定的 Playwright 自带版本，不使用系统 Chrome 或无头模式。

在 Helm 源码根目录安装并构建：

```sh
export HELM_SOURCE="$PWD"
npm ci --cache /private/tmp/helm-npm-cache
npm run build --cache /private/tmp/helm-npm-cache
npm run browser:install --cache /private/tmp/helm-npm-cache
```

创建一份新运行目录。`init` 建空项目、`main` 的空提交、本地裸远端 `origin.git`，并推送初始空提交以设置跟踪分支；不写产品文件。每次重跑使用一个新目录，已有目录会被拒绝。后续只有运行层在审核接受后推送产品改动。

```sh
export HELM_RUN="$(node scripts/2048-e2e.mjs init)"
echo "$HELM_RUN"
node scripts/2048-e2e.mjs serve "$HELM_RUN"
```

`serve` 前台启动独立 `helmd`，用随机回环端口和 `$HELM_RUN/data`，显式注入真实 Claude 调度者、执行者驱动；输出 URL/PID，保存 `daemon.json`。同一目录只启动一个服务。保持该终端运行，最后 Ctrl-C 正常停止；中断后继续使用同一目录可执行 `serve`，由启动对账处理未结束的派单。普通 `helm serve` 当前默认使用假调度者，本步骤必须使用上面的脚本。

在第二个终端设置前面输出的路径，定义 `helm` 为本次服务的 CLI 包装（实际执行 `dist/src/cli.js`，所有状态读取与操作都经 CLI 和 HTTP）：

```sh
export HELM_SOURCE=/absolute/path/to/Helm
export HELM_RUN=/absolute/path/printed/by/init
helm() { node "$HELM_SOURCE/scripts/2048-e2e.mjs" helm "$HELM_RUN" "$@"; }
node "$HELM_SOURCE/scripts/2048-e2e.mjs" start "$HELM_RUN"
export WORK_ID="$(node -p 'JSON.parse(require("fs").readFileSync(process.env.HELM_RUN + "/work.json", "utf8")).workId')"
helm list-agent-templates
helm list-pending
helm get-conversation --workId "$WORK_ID"
helm get-work-descriptions --workId "$WORK_ID"
```

`start` 先把两个内置模板设成 `haiku` / `low`、并发上限设为 2，再登记项目并通过 `helm send-message` 发起 2048 工作。消息含玩法、存档、测试和浏览器截图标准，要求 4～5 张有依赖的卡片（含整体验收），允许出现问题后新增返工/修复卡片。重复 `start` 使用原 key，返回同一项工作。不要在派单运行中重复 `start` 修改设置。

用户只在下面三个地方作决定，不手工建卡片、派单或标完成。

1. 确认工作说明：等待调度者起草完，从 `list-pending` 读确认关卡的 `id`、`description.id`、`baseRef`、`baseCommit` 和脏文件提醒，核对需求/边界/标准与 `main` 基准。需要修改就发消息，等待新草稿；确认时传入实际查看的版本 id。

   ```sh
   helm send-message --workId "$WORK_ID" --gateId '<确认关卡id>' --key clarify-1 --body '请把……写入工作说明'
   helm decide-gate --workId "$WORK_ID" --gateId '<确认关卡id>' --descriptionId '<工作说明版本id>' --decision confirm
   ```

2. 一般决策关卡：用 `list-pending` / `get-conversation` 读问题、正文与选项。可先追问；明确后选择实际选项的原文或写自由回答。工作说明变更仍须另走确认关卡。

   ```sh
   helm send-message --workId "$WORK_ID" --gateId '<决策关卡id>' --key question-1 --body '请说明……'
   helm decide-gate --workId "$WORK_ID" --gateId '<决策关卡id>' --decision '<选项原文或自由回答>'
   ```

3. 审核：等待 `list-pending` 出现 `kind=review`，查看逐卡汇总报告、`review.diff`、整体验收结论、被拒绝操作数和未声明结论数。核对截图及测试证据后接受，或附意见退回；退回后等待新的审核关卡，不复用旧关卡。

   ```sh
   helm get-conversation --workId "$WORK_ID"
   helm decide-gate --workId "$WORK_ID" --gateId '<审核关卡id>' --decision return --comment '文件:行：需要修正……'
   # 满足标准时，对当前待决定审核关卡执行：
   helm decide-gate --workId "$WORK_ID" --gateId '<审核关卡id>' --decision accept
   ```

执行和验收期间按需读取（不用一直盯终端）：

```sh
helm get-work --workId "$WORK_ID"
helm get-card-graph --workId "$WORK_ID"
helm list-dispatches --workId "$WORK_ID"
helm get-dispatch --workId "$WORK_ID" --dispatchId '<派单id>'
helm get-dispatch-output --workId "$WORK_ID" --dispatchId '<派单id>'
helm get-dispatch-artifacts --workId "$WORK_ID" --dispatchId '<派单id>'
helm get-events --workId "$WORK_ID"
```

核对有依赖的 4～5 张初始卡片、独立的新上下文验收派单、页面验收的 `needsBrowser=true`、整体验收仅有验收派单且依赖所有其他卡片。浏览器验收期间必须查看截图：从成果列表找到 `browser/*.png` 对应的 `path`，用本机图片查看器打开，按工作说明核对初始棋盘、移动、计分、存档恢复、重开。浏览器文件保存在 `$HELM_RUN/data/dispatches/<派单id>/browser/`，结束后另存为成果，不依赖临时卡片副本。也可通过 `helm read-artifact --workId "$WORK_ID" --artifactId '<成果id>' --encoding base64` 导出。不得只看验收者文字就算截图通过。若截图不足，审核退回并注明缺少哪项证据。

不刻意制造冲突。若遇 `WORK_BRANCH_CONFLICT`，检查新建的修复卡片 `repairOfCardId`、其合并记录，以及修复完成后原卡片完成的事件。执行者额度用完时应由调度者改派或提关卡。调度者额度用完/连续失败导致运行层暂停时，先通过 `list-pending` 读原因、解决原因后运行 `helm resume-work --workId "$WORK_ID"`；不要自动重试。需要停止开销时用 `helm pause-work --workId "$WORK_ID"`，处理后再恢复。

审核接受后，核对 `get-work` 为 `completed`，事件中 `base-merge-result` 为 `merged` / `already-contained`、`base-push-result` 为 `pushed`。再检查基准分支与本地远端（`work-completed` 本身不足以证明合并/推送成功）：

```sh
git -C "$HELM_RUN/project" log --oneline --graph main
git -C "$HELM_RUN/project" status --short
git -C "$HELM_RUN/project" rev-parse main
git --git-dir="$HELM_RUN/origin.git" rev-parse main
git -C "$HELM_RUN/project" ls-tree -r --name-only main
```

两个 SHA 应相同且与 `run.json` 中的 `baseline` 不同。按生成项目 README 的命令，从基准分支安装、构建、启动游戏，使用空闲本机端口，亲自确认可玩并截图；该人工浏览器检查也只在沙箱外执行。不要从卡片副本内开终端：派单收尾会清理其中的进程。

保持 `helmd` 运行，待本轮结束、没有运行中/排队派单后导出证据：

```sh
node "$HELM_SOURCE/scripts/2048-e2e.mjs" export "$HELM_RUN"
cat "$HELM_RUN/evidence/timeline.txt"
```

导出可重复执行，覆盖当前快照：`snapshot.json` 保存工作、卡片图、每次派单最终回答/模板/模型/会话/验收结果/token、全部事件、成果索引、工作说明和对话；`timeline.txt` 逐卡列完成执行派单、最近验收结论、派单历史、token（另列调度轮次和工作总计）及事件顺序，并列拒绝、失败、暂停和合并/推送结果。运行中导出仅代表当时进度，不代表最终验收。保留整个运行目录以保存截图、成果、轮次及派单原始输出。

第二段执行者将这份摘要、实际命令/结果、截图查看结论、发现的问题和运行目录追加到既有 `.scratch/tasks/p1-15/report.md`，保留首行 session-id，再完成任务单剩余勾选并将 Status 改为 resolved。没有真实跑通前保持待验收项未勾选。
