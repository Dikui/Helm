# 第二阶段 2048：Codex 调度者、Claude/Codex 执行者与交叉验收

这是[第二阶段任务单 13](../.scratch/helm-v1-p2/issues/13-codex-coordinator-2048-e2e.md)的手动运行材料，对应 [spec 的端到端验收](../.scratch/helm-v1-p2/spec.md#testing-decisions)。以下安装服务、发起工作及浏览器核对均在沙箱外、有桌面会话的 macOS 机器上执行，会消耗本机 Claude 和 Codex 订阅额度并启动有界面的 Chrome for Testing。本脚本不在 `npm test` 中；准备材料时不执行这些步骤。

准备 Node >=22.13、支持 `merge-tree --write-tree` 的 git、本机已登录的 `claude` 和 `codex`（两者的 `--version` 可用），以及本机沙箱依赖 lsof。保持 CLI 的默认主目录和现有登录，勿把 `HOME` 改到临时目录。浏览器使用锁定的 Playwright 自带版本，不使用系统 Chrome 或无头模式。

按 [ADR 0005](../docs/adr/0005-subscription-templates-use-default-cli-homes.md)，订阅模板不设 `CLAUDE_CONFIG_DIR` / `CODEX_HOME`，用户全局规则、hooks、插件、MCP 和 skills 正常进入，会话记录允许进入 `~/.claude/projects/`、`~/.codex/sessions/`。任务单旧的“没有新增记录”检查与该 ADR 冲突，不作为本轮通过条件。内置模板显式覆盖模型、推理强度和 fast：Claude 两个模板均为 `haiku` / `low` / `false`，Codex 两个模板均为 `gpt-6-luna` / `low` / `false`，不跟随用户默认模型。ChatGPT 账号下使用可用的低价模型 `gpt-6-luna`，不用 `gpt-5.4-mini`。

在 Helm 源码根目录安装并构建：

```sh
export HELM_SOURCE="$PWD"
npm ci --cache /private/tmp/helm-npm-cache
npm run build --cache /private/tmp/helm-npm-cache
npm run browser:install --cache /private/tmp/helm-npm-cache
```

确认 4242 没有旧的手动 `helm serve` 占用；如有，在原终端 Ctrl-C 正常停掉后再安装服务。使用刚构建的 CLI 安装用户级服务，保留当前 PATH 和代理配置：

```sh
node dist/src/cli.js service install
launchctl print gui/$(id -u)/io.helm.helmd
tail -n 80 ~/.helm/logs/helmd.stdout.log ~/.helm/logs/helmd.stderr.log
node dist/src/cli.js get-settings --url http://127.0.0.1:4242
```

核对 LaunchAgent 正在运行、日志无端口占用或驱动启动错误，`get-settings` 成功返回。服务监听默认 `http://127.0.0.1:4242`，任务库及输出在 `~/.helm/`，由 launchd 保持运行；不要再启动脚本或手动 `helm serve`。脚本所有 HTTP 操作都使用该地址，可用 `HELM_URL` 覆盖以连接另一个已安装服务；它不会安装或启动服务，也不读取 `daemon.json`。服务安装本身不受 `HELM_URL` 影响。

创建一份新运行目录。`init` 建空项目、`main` 的空提交、本地裸远端 `origin.git`，并推送初始空提交以设置跟踪分支；不写产品文件。每次重跑使用一个新目录，已有目录会被拒绝。后续只有运行层在审核接受后推送产品改动。

```sh
export HELM_RUN="$(node scripts/2048-e2e.mjs init)"
echo "$HELM_RUN"
```

定义 `helm` 为服务的 CLI 包装（实际执行 `dist/src/cli.js`，所有状态读取与操作都经 CLI 和 HTTP）。换终端时重新设置 `HELM_SOURCE`、`HELM_RUN`，若设置了 `HELM_URL` 也需保持一致：

```sh
export HELM_SOURCE=/absolute/path/to/Helm
export HELM_RUN=/absolute/path/printed/by/init
helm() { node "$HELM_SOURCE/scripts/2048-e2e.mjs" helm "$HELM_RUN" "$@"; }
helm get-settings
helm list-agent-templates
node "$HELM_SOURCE/scripts/2048-e2e.mjs" start "$HELM_RUN"
export WORK_ID="$(node -p 'JSON.parse(require("fs").readFileSync(process.env.HELM_RUN + "/work.json", "utf8")).workId')"
helm list-agent-templates
helm list-pending
helm get-conversation --workId "$WORK_ID"
helm get-work-descriptions --workId "$WORK_ID"
```

发起前核对四个模板可用、模型/推理强度/fast 与上述设置一致。`start` 通过现有用户操作把全局执行者并发上限设为 2，再登记项目并通过 `send-message --coordinatorTemplateId codex-coordinator` 发起工作；不修改模板文件或用户默认模型。此并发设置影响同一服务的其他工作，先记下 `get-settings` 的原值，结束后按需用 `helm set-concurrency --limit '<原值>'` 恢复。

消息含玩法、存档、测试和浏览器截图标准，要求 4～5 张有依赖的初始卡片（含整体验收）、两家都有执行派单、每张实现卡片由另一家验收、页面相关验收及整体验收用浏览器。整体验收只派验收单，由两家分别覆盖另一家的实现。允许验收不通过后在同一卡片返工、出现合并冲突后建修复卡片。重复 `start` 使用原 key，返回同一项工作；不要在运行中重复 `start` 修改全局并发。

用户只在下面三个地方作决定，不手工建卡片、派单或标完成。

1. 确认工作说明：等待调度者起草完，从 `list-pending` 读确认关卡的 `id`、`description.id`、`baseRef`、`baseCommit` 和脏文件提醒，核对需求/边界/标准与 `main` 基准。需要修改就发消息，等待新草稿；确认时传入实际查看的版本 id。

   ```sh
   helm send-message --workId "$WORK_ID" --gateId '<确认关卡id>' --key clarify-1 --body '请把……写入工作说明'
   helm decide-gate --workId "$WORK_ID" --gateId '<确认关卡id>' --descriptionId '<工作说明版本id>' --decision confirm
   ```

2. 一般决策关卡：用 `list-pending` / `get-conversation` 读问题、正文与选项。可先追问；明确后选择实际选项的原文或写自由回答。工作说明变更仍须另走确认关卡。

   ```sh
   helm send-message --workId "$WORK_ID" --gateId '<决策关卡id>' --key question-1 --body '请说明……'
   helm decide-gate --workId "$WORK_ID" --gateId '<决策关卡id>' --decision '<选项原文或自由回答>'
   ```

3. 审核：等待 `list-pending` 出现 `kind=review`，查看逐卡汇总报告、`review.diff`、整体验收结论、被拒绝操作数和未声明结论数。核对截图及测试证据后接受，或附意见退回；退回后等待新的审核关卡，不复用旧关卡。

   ```sh
   helm get-conversation --workId "$WORK_ID"
   helm decide-gate --workId "$WORK_ID" --gateId '<审核关卡id>' --decision return --comment '文件:行：需要修正……'
   # 满足标准时，对当前待决定审核关卡执行：
   helm decide-gate --workId "$WORK_ID" --gateId '<审核关卡id>' --decision accept
   ```

执行和验收期间按需读取（不用一直盯终端）：

```sh
helm get-work --workId "$WORK_ID"
helm get-card-graph --workId "$WORK_ID"
helm list-dispatches --workId "$WORK_ID"
helm get-dispatch --workId "$WORK_ID" --dispatchId '<派单id>'
helm get-dispatch-output --workId "$WORK_ID" --dispatchId '<派单id>'
helm get-dispatch-artifacts --workId "$WORK_ID" --dispatchId '<派单id>'
helm get-events --workId "$WORK_ID"
```

核对有依赖的 4～5 张初始卡片、独立的新上下文验收派单、页面相关验收及整体验收的 `needsBrowser=true`、整体验收仅有验收派单且依赖所有其他卡片。逐张核对执行与验收的模板快照/驱动：`claude-executor`（`claude-sdk`）执行交 `codex-executor`（`codex`）验收，反向也必须出现；返工后的验收仍应交给与该次执行不同的一家。整体验收卡片没有执行者，核对其两家验收派单覆盖另一家完成的实现。

浏览器验收期间必须查看截图：从成果列表找到 `browser/*.png` 对应的 `path`，用本机图片查看器打开，按工作说明核对初始棋盘、移动、计分、存档恢复、重开。默认服务的浏览器文件位于 `~/.helm/dispatches/<派单id>/browser/`，以成果返回的实际路径为准；结束后另存为成果，不依赖临时卡片副本。也可通过 `helm read-artifact --workId "$WORK_ID" --artifactId '<成果id>' --encoding base64` 导出。不得只看验收者文字就算截图通过。若截图不足，审核退回并注明缺少哪项证据。

不刻意制造冲突。若遇 `WORK_BRANCH_CONFLICT`，检查新建的修复卡片 `repairOfCardId`、其合并记录，以及修复完成后原卡片完成的事件。执行者额度用完时应由调度者改派或提关卡。调度者额度用完/连续失败导致运行层暂停时，先通过 `list-pending` 读原因、解决原因后运行 `helm resume-work --workId "$WORK_ID"`；不要自动重试。需要停止开销时用 `helm pause-work --workId "$WORK_ID"`，处理后再恢复。

审核接受后，核对 `get-work` 为 `completed`，事件中 `base-merge-result` 为 `merged` / `already-contained`、`base-push-result` 为 `pushed`。再检查基准分支与本地远端（`work-completed` 本身不足以证明合并/推送成功）：

```sh
git -C "$HELM_RUN/project" log --oneline --graph main
git -C "$HELM_RUN/project" status --short
git -C "$HELM_RUN/project" rev-parse main
git --git-dir="$HELM_RUN/origin.git" rev-parse main
git -C "$HELM_RUN/project" ls-tree -r --name-only main
```

两个 SHA 应相同且与 `run.json` 中的 `baseline` 不同。按生成项目 README 的命令，从基准分支安装、构建、启动游戏，使用空闲本机端口，亲自确认可玩并截图；该人工浏览器检查也只在沙箱外执行。不要从卡片副本内开终端：派单收尾会清理其中的进程。

保持 `helmd` 运行，待本轮结束、没有运行中/排队派单后导出证据：

```sh
node "$HELM_SOURCE/scripts/2048-e2e.mjs" export "$HELM_RUN"
cat "$HELM_RUN/evidence/timeline.txt"
```

导出可重复执行，覆盖当前快照：`snapshot.json` 保存工作、卡片图、每次派单最终回答/模板/模型/会话/验收结果/token、全部事件、成果索引、工作说明和对话，以及当前模板与设置；历史配置以轮次/派单快照为准。`timeline.txt` 列出每个调度轮次的模板/驱动/模型/推理强度/fast/输出路径、逐卡派单的模板与驱动、最近验收结论、token（另列调度轮次和工作总计）及带模板/驱动的事件顺序，并列拒绝、失败、暂停和合并/推送结果。核对每个轮次均为 `codex-coordinator`，逐卡检查两家交叉验收。运行中导出仅代表当时进度，不代表最终验收。

工作结束且所有派单和调度轮次停止后，等待后台压缩完成。以下只读检查使用导出快照中的实际路径，逐个验证派单步骤和轮次输出仅剩 `.gz`、可解压，并通过 `get-dispatch-output` 读回全部派单内容与 gzip 内容比较（需要在服务所在机器上执行）：

```sh
node --input-type=module <<'NODE'
import assert from 'node:assert/strict';
import { execFileSync } from 'node:child_process';
import { existsSync, readFileSync, readdirSync } from 'node:fs';
import { join } from 'node:path';
import { gunzipSync } from 'node:zlib';
const snapshot = JSON.parse(readFileSync(join(process.env.HELM_RUN, 'evidence/snapshot.json'), 'utf8'));
assert.equal(snapshot.work.status, 'completed');
const cli = join(process.env.HELM_SOURCE, 'dist/src/cli.js');
const url = process.env.HELM_URL ?? 'http://127.0.0.1:4242';
const compressed = path => {
  assert.equal(existsSync(path), false, `仍有未压缩输出：${path}`);
  return gunzipSync(readFileSync(`${path}.gz`)).toString('utf8');
};
for (const dispatch of snapshot.dispatches) {
  assert.equal(dispatch.status, 'ended');
  const files = readdirSync(dispatch.outputPath).filter(name => /^\d+\.json(?:\.gz)?$/.test(name));
  assert.ok(files.length > 0, `派单没有输出，需检查结束原因：${dispatch.id}`);
  const expected = files.sort((a, b) => parseInt(a) - parseInt(b))
    .map(name => JSON.parse(compressed(join(dispatch.outputPath, name.replace(/\.gz$/, '')))));
  const response = JSON.parse(execFileSync(process.execPath, [cli, 'get-dispatch-output',
    '--workId', snapshot.work.id, '--dispatchId', dispatch.id, '--url', url],
    { encoding: 'utf8', maxBuffer: 64 * 1024 * 1024 }));
  assert.equal(response.ok, true);
  assert.deepEqual(response.result, expected);
  console.log(`派单 ${dispatch.id}：${expected.length} 个 gzip 步骤，CLI 内容一致`);
}
const rounds = snapshot.events.filter(event => event.action === 'round-started');
assert.ok(rounds.length > 0, '没有调度轮次');
for (const round of rounds) {
  assert.ok(snapshot.events.some(event => event.action === 'round-ended' && event.object.id === round.object.id),
    `轮次尚未结束：${round.object.id}`);
  compressed(round.details.outputPath);
  console.log(`轮次 ${round.object.id}：gzip 可解压，原文件已移除`);
}
NODE
```

若仍有原文件，稍等压缩完成后重新导出并检查；缺文件、输出被删除或内容不一致均不算通过。调度轮次目前没有用户读取输出命令，以上直接检查其 gzip。不要手工压缩来代替运行层的结果，也不要在核对前删除输出。脚本 `export` 只导出材料，不会触发压缩；如需完整搬走输出与截图，可在核对后执行 `helm export-outputs --workId "$WORK_ID" --targetPath "$HELM_RUN/outputs.tar.gz"`（目标必须不存在）。保留运行目录和该归档；服务原始输出不在运行目录下，单独保留运行目录并不能保存它们。
